# hahifuhe-quality-reviewer 観点集（lenses）

`hahifuhe-quality-reviewer`（= `/hahifuhe:review-quality`）が **baseline 4 軸に上乗せして読む学習観点**。
`agents/hahifuhe-quality-reviewer.md` の「評価 4 軸」が安定 core、ここは
**人間レビュアーの指摘から蒸留して育つ層**（`/hahifuhe:review-retro` が追記する）。

各観点は **観点（何を見るか）/ 範囲（どこを）/ 目線（守る実害）/ 検出（どう見つけるか）** のユニットで持つ。

- これは「ケースの山」ではなく、過去傾向を**蒸留した有界な観点**。reviewer はこの集合だけを読む（コンテキスト一定）。
- **上限の目安 20 観点**。超過 or 定期で**統合**（近接マージ・陳腐化剪定・安定したものは core `hahifuhe-quality-reviewer.md` の 4 軸へ昇格）。
- 生のケース履歴は別ファイル（`agents/hahifuhe-review.cases.jsonl`。プロジェクトごとに retro で育てる学習データで、初期状態では存在しない）に退避し、**ここには溜めない**（provenance もそちら）。
- 目線（実害カテゴリ）= `correctness / security / performance / UX / 保守性・結合度`。
  **結合度・疎結合・責務の置き場・命名・依存方向**は軸1（アーキテクチャ準拠）の延長として**実害扱いで残す**
  （人間レビュアーの指摘の主戦場。bugbot 側の「保守性のみは参考に落とす」ゲートとは扱いを変える）。
- 初版は空。retro を回すまでは baseline 4 軸のみで動く。

### Q1. 接点リソースの producer 参照は名前参照で疎結合に（実体参照に逆戻りさせない）

- **観点**: 複数ドメインから送られる「接点」になりつつあるリソース（エンジン系 SQS 等。webhook/トラッキング等複数経路から enqueue される）の **producer 側参照を、実体参照（CDK の `IQueue` 等オブジェクト渡し）ではなく名前参照（文字列リソース名 → ARN/URL を自前で組み立て）** にして、producer をリソース実体から疎結合させているか。プロジェクト内に名前参照で配線している既存お手本があれば同形か。
- **範囲**: CDK（`cdk/`）。stack/construct をまたぐ参照、および同一スタック内でも「接点」リソースの producer 配線。
- **目線**: 保守性・結合度（人間レビュアーの指摘が集中しやすい領域）。実体参照のままだと将来のキュー変更や FIFO↔standard 切替時に「参照されていて消せない」→ 新名称キュー作成＋向き先切替＋旧キュー空 Lambda 化＋2回デプロイ、という2段階デプロイを強いられる。名前参照なら普通に消せる。
- **検出**: producer が `xxxQueue.grantSendMessages(role)` や `queue.queueUrl`/`queue.queueArn` のように実体オブジェクトに依存していたら、名前参照（`if (name) { role.addToPolicy(new PolicyStatement({ actions:['sqs:SendMessage'], resources:[arn 文字列] })) }` ＋ env も名前から URL 組み立て）に置換できないか見る。
- **例外（実体参照で可）**: そのリソースしか使わない IAM や、consumer の event source（`addEventSource` / `grantConsumeMessages`）等、対象 Lambda と一緒に消えて問題ないライフサイクル一蓮托生のものは実体参照で可。これは「疎結合に逆行」と誤指摘しない。
- **由来**: チームの CDK レビュアーによる過去レビューの実例。接点キューの producer 側を実体参照→名前参照へ戻した修正から蒸留。

### Q2. 境界（認証/認可・IaC 設定）の回帰ガードを謳うテストが検証層を取り違えていないか

- **観点**: 「authorizer 非適用の回帰ガード」「認証境界の回帰防止」等を名乗るテストが、実際には下層（Hono/ハンドラを `app.request` で直接叩く等のアプリ層）しか検証しておらず、その境界が実際に効く層（API Gateway の authorizer 設定＝IaC/CDK template）を検証していないことはないか。テスト名・コメントが実カバレッジを過大表現していないか。既に検証基盤（CDK assertion test 等）があるのに対象に含めていないか。
- **範囲**: 公開・未認証経路の新設、認証/認可境界に触れる変更。テスト（`*.test.ts`）とその対象層（アプリ層 vs IaC/template 層）。
- **目線**: correctness・security（境界回帰の検知漏れ）・保守性（テスト名が保証を偽る）。境界設定が IaC 側にあるのにアプリ層テストで代用すると、authorizer の付け外し回帰を誰も検知できず、テスト名だけが安全を主張する。
- **検出**: 「回帰ガード」「境界」を謳うテストの実体を読み、`app.request`/ハンドラ直叩きで終わっていないか確認。境界が CDK/template 定義なら CDK assertion test（`cdk/test/constructs/**` 等）に同等ガードがあるか探す。無ければ「テスト名を実態（アプリ層のみ）に補正、または IaC レベルの assertion を1本追加」を指摘。

### Q3. 新規メソッド/シンボルが既存の不正確・冗長命名を踏襲して語彙債を伝播していないか

- **観点**: 新規追加した method/関数/引数の名前が、実際に触る対象（DB カラム名・戻り値・ドメイン語彙）と乖離していないか。既存の不正確・冗長な命名（例: カラムは `entryCode` なのに method は `findCoreByEntryUrlCode` と "Url" が冗長）を「既存に揃える」名目で踏襲し、命名債を新コードへ伝播していないか。
- **範囲**: 新規 method/関数/引数の命名。特に repository 層（カラム名との整合）・公開 export のシンボル名。
- **目線**: 保守性（命名）。名と実体の乖離は誤読を生み、既存債の伝播は将来の横断改名コストを増やす（命名は人間レビュアーの指摘が集中しやすい領域の一つ）。
- **検出**: 新規シンボル名の各語が実体（WHERE 対象カラム・引数の実値・戻り値の意味）と一致するか照合。既存の類似命名を踏襲している場合は「既存も含む横断改名 or 最低限コメントで実体（どのカラムを引くか）を明記」を任意指摘。新規ミスか既存債の伝播かを区別して severity を付ける（伝播は通常 Minor/任意）。

### Q4. インフラ直叩き（関心の分離違反 = 単体テスト不能なコード）

- **観点**: UI コンポーネント・hook・domain/service 層のモジュールが、HTTP クライアント（fetch/axios）・AWS SDK（`@aws-sdk/*`）・DB クライアント（drizzle/pg 直）・外部 API のエンドポイント URL リテラルを**直接 import・呼び出し**していないか。正しい形は repository / client 抽象（例: `@yourorg/data-access` の repository・共有パッケージの外部 API client 等）を経由し、モジュールには依存を注入する。
- **範囲**: 新規・変更ファイルの import 追加行と URL/エンドポイント リテラル。特にフロントエンド apps の component/hook、各 apps の service/usecase 層、`packages/*` のドメインロジック。
- **目線**: 保守性・結合度＋テスト可能性（閣下の明示要望 2026-07-06）。インフラ直叩きのモジュールは**単体テストに実 API・実 DB が必要になり、実質テストが書けない**。指摘には必ずこの実害（「このままだと〜のテストにモックでなく実環境が要る」）を1行添える。
- **検出**: diff の import 追加を層と照合する。domain/UI 層ファイルに `fetch(`・`axios`・`@aws-sdk/`・`new Client(`（pg 等）・`https://api.` 等のリテラルが現れたら、既存の抽象（repository・client wrapper）が同リポに存在するか探し、あれば「それを注入する形へ」、無ければ「境界モジュールの新設」を指摘する。既存コードが同違反をしている場合は「既存事項・本 PR 非由来」と明記し、**新規追加分だけ**をブロッカー候補にする。
- **例外（誤指摘しない）**: インフラ層そのもの（repository 実装・client wrapper・Lambda handler のエントリ・スクリプト/バッチの main）が SDK を直接使うのは正しい配置。テストコード内の直叩きも対象外。

### Q5. 間違えにくい設計か（防御的設計 = 呼び出し側の「覚えごと」を増やしていないか）

- **観点**: 変更が導入・変更する公開シンボル（関数・型・モジュール境界）が、正しく使うために**呼び出し側の記憶に頼る構造**になっていないか。症状は3パターン。①**型が許すのに壊れる入力がある**: シグネチャ上は受け取れるが、本文の throw / early-return / 暗黙の誤動作で拒否する（= 事前条件が型に載っていない）。②**不正な状態が型で表現できる**: optional・boolean・string の組み合わせで、業務上ありえない組み合わせがコンパイルを通る。③**同じガードを呼び出し側ごとに書かせる**: 境界で1度パース/検証すれば済むものを、各利用箇所に null チェック・形式チェックとして複製させる。個々のガード漏れ（bugbot L4 等が拾う症状）の**上流にある「漏れを生みやすい構造」**を問う。
- **範囲**: 新規・変更の公開シンボル。特に exported 関数のシグネチャ（引数の組・戻り値の型）、複数の呼び出し元を持つ共有関数、repository/service/usecase 層の新規 API。単一呼び出し元の private ヘルパは対象外（指摘コストに実害が見合わない）。
- **目線**: correctness・保守性。「覚えごと」依存の API は、**今回の diff で全呼び出し側が正しくても、次に呼ぶ人（未来の PR）が同じ穴を踏む**。ガード漏れを1件ずつ潰しても再発する構造をここで断つ。防御的プログラミング（ガードを足す）の前段にある「そもそもガードが要らない・1箇所で済む設計か」を見る。
- **検出**: ①新規 exported 関数のシグネチャと本文を突き合わせ、「型は許すが本文が拒否する入力」（throw・early-return・`!` 非 null 断定）を洗う。コメントやドキュメントの「〜の後に呼ぶこと」「〜が前提」は**事前条件が型に載っていない自白**として拾う。②新規型の optional/boolean の組み合わせを列挙し、ありえない組み合わせが表現可能なら、判別可能ユニオン・必須化・パース済み型（値オブジェクト）への変更を任意提案。③diff 内で同形のガード（同じ null/形式チェック）が2箇所以上に複製されていたら、境界（コンストラクタ・ファクトリ・パーサ）1箇所への集約を提案。**指摘には必ず誤用シナリオを1行添える**（「どの呼び出し側が・何を忘れると・何が壊れる」を言語化できない指摘は出さない）。
- **重大度の既定**: 誤用シナリオが具体的で本番到達性がある場合のみ Major。それ以外（将来リスク・設計改善提案）は Minor/任意提案に留める。reviewer 本体の「スタイル不問・80%確信」原則に従い、**代替設計を具体的に示せない指摘は出さない**。
- **例外（誤指摘しない）**: 既存コードが同じ前提依存をしている場合は「既存事項・本 PR 非由来」と明記し、新規追加分のみブロッカー候補にする。`context.json`・コメント・設計書に意図的な選択の根拠（性能・外部 API 制約等）があるものは「確認事項」へ落とす（設計判断を品質問題と誤認しない）。テストコード・単発スクリプトは対象外。
- **由来**: 閣下要望（2026-07-08）。「設計の不備で考慮すべき点が増え、不具合につながる構造を防御的設計の観点で見たい」。責務分担・テスト可能性（Q4）と対で、レビューを「設計書どおりか」から「設計として筋が良いか」へ広げる位置づけ。
