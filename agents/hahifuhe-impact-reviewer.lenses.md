# hahifuhe-impact-reviewer 観点集（lenses）

`hahifuhe-impact-reviewer`（= `/hahifuhe:review-impact`）が **baseline 観点に上乗せして読む学習観点**。
`agents/hahifuhe-impact-reviewer.md` の「影響分析の観点」が安定 core、ここは
**人間レビュアーの指摘から蒸留して育つ層**（`/hahifuhe:review-retro` が追記する）。

各観点は **観点（何を見るか）/ 範囲（どこを）/ 目線（守る実害）/ 検出（どう見つけるか）** のユニットで持つ。

- これは「ケースの山」ではなく、過去傾向を**蒸留した有界な観点**。reviewer はこの集合だけを読む（コンテキスト一定）。
- **上限の目安 20 観点**。超過 or 定期で**統合**（近接マージ・陳腐化剪定・安定したものは core `hahifuhe-impact-reviewer.md` へ昇格）。
- 生のケース履歴は別ファイル（`agents/hahifuhe-review.cases.jsonl`。プロジェクトごとに retro で育てる学習データで、初期状態では存在しない）に退避し、**ここには溜めない**（provenance もそちら）。
- 目線（実害カテゴリ）= `correctness / security / performance / UX / 保守性・結合度`。
- 初版は空。retro を回すまでは baseline 観点のみで動く。

### I1. 接点リソースの実体参照は「削除不能（deadly embrace）」の波及を生む

- **観点**: 接点リソース（複数経路から使われる SQS 等）への**実体参照**を新規導入 or 温存することで、stack 間 or construct 間に Ref/`Fn::GetAtt`/Export 依存が生まれ、将来そのリソースを変更・削除する際にデプロイが deadlock（参照されていて消せない → cross-stack 参照除去は2回デプロイ必須）しないか。
- **範囲**: CDK（`cdk/`）。stack をまたぐ参照、同一スタック内でも接点リソースの実体オブジェクト渡し。
- **目線**: correctness（デプロイ可能性）・保守性。CDK の "deadly embrace"（cross-stack 参照を消すとデプロイがデッドロックし、producer に `exportValue()` を足して deploy →外して再 deploy の2段階を強制される）。プロジェクトルール「スタック**間**参照はやめろ」にも反する。
- **検出**: diff が新たに実体オブジェクト（`xxxConstruct.queue` 等）を別 construct/stack の props へ渡していないか。名前参照（文字列名→ARN/URL 手組み）で代替できる接点なら指摘する。consumer の event source 等ライフサイクル一蓮托生のものは対象外（→ quality Q1 例外と同じ）。
- **由来**: チームの CDK レビュアーによる過去レビューの実例。詳細は quality 観点 Q1 と同根。

### I2. 廃止予定モジュールに新規変更・新規依存を足していないか

- **観点**: 変更が、プロジェクトで**廃止予定と宣言されたモジュール**（例: 移行中の旧 API サーバ）を**新規に変更・機能拡張**、またはそこへの**新規依存・配線**を足していないか。廃止予定モジュールがある場合、新規実装は後継側へ置くのが方針。
- **範囲**: 全 diff。特に新規 API route / Service 層 / RPC スキーマ / IaC 配線・依存追加。
- **目線**: 保守性・方向性。廃止予定モジュールへの新規投資は方向逆行＝即・技術的負債。既存実装の最小保守（廃止までの凍結維持）は可だが、それを超える拡張・新規追加は要確認。
- **検出**: diff のパスに廃止予定モジュール配下の新規追加・機能拡張がないか。新規ルート/サービスが後継側でなく旧側に置かれていないか。旧トランスポート/スキーマ（廃止予定の RPC 定義等）への新規追加は移行方針に反しないか。
- **由来**: 元プロジェクトの API 移行方針（廃止予定の旧 API サーバへの新規追加禁止）。導入先プロジェクトでは、自プロジェクトの廃止予定モジュール・移行方針（design doc 等）に読み替えて適用する。

### I3. 削除/リネームの波及は「コード参照」だけでなく docs・コメント・設定の名指し参照まで見る

- **観点**: ファイル・シンボル・設定キーを**削除/リネーム**したとき、その名前を**コード（import/export/dynamic import）以外**＝ docs / README / 設計書 / コード内コメント / 設定ファイルの**例示・サンプル列挙**が名指し参照していないか。残ると stale reference（実体と食い違うドキュメント例示）になる。
- **範囲**: 削除・リネームを含む diff 全般。特に `docs/**`・`*.md`・README・近接コメント・設定/サンプルの列挙箇所。
- **目線**: 保守性（ドキュメントと実体の乖離＝後続読者の混乱）・correctness（例示が実在しない＝動かない手順）。
- **検出**: 削除/リネームした basename・シンボル名を `git grep`（or Serena `search_for_pattern`）で**コード以外も横断**し、残存する名指し参照を洗う。**import/export のコード参照ゼロ確認だけで「波及なし」と結論しない**（コード緑でも docs は腐る）。
