# PR レビュー投稿コメントの体裁（正本）

Global CLAUDE.md「他人の PR をレビューするとき」3点目から退避した詳細。
閣下が実際に投稿している GO/NO-GO コメントの体裁を固定する。**下書きは必ずこの型で出す**
（初回に `## ブロッキング`/`## LGTM` だけの簡易見出しで出して差し戻された 2026-07-04 の反省が発端）。

出典（実例・この型の抽出元）: 過去レビューの実例（複数 PR の approve コメント本文）。

## 骨格（重大度降順・見出しだけで結論が分かる状態にする）

1. **冒頭メンション（必須）**: コメント 1 行目に PR 作者へのメンションを置く（`@<作者の GitHub ID> `）。作者 ID は `gh pr view <N> --json author -q .author.login` で機械取得し、推測で書かない（2026-07-23 閣下指示: メンション無しで投稿していたのを改善）。

2. **前置き 1 行**: 何を回して/確認したかを正直に。
   - review-all を回した → 「レビューオール（整合性/要件/設計/変更影響/品質/テスト健全性/セキュリティ/BugBot観点 + Codex）を回しました。」
   - 手動で差分を読んだだけ → 「差分を読み、挙動の正しさを一次情報（実コード・schema・repository）で追いました。」と書く（回していない review-all を回したと言わない＝epistemic honesty）。

3. **`## 総合（<判定>）`** — 見出し自体に判定を括弧で入れ、一目で「結局 GO なのか」が分かる状態にする（`## 総合` だけで結論を本文まで読ませない＝差し戻し実例 2026-07-08 過去レビューの実例）。判定語は `LGTM` / `GO` / `NO-GO` / `要修正`。本文は続けて太字で言い切る。
   - ブロッカー無し: 見出し `## 総合（LGTM）`（または `## 総合（GO）`）+ 本文 `**コードは LGTM 相当（GO）** です。要修正（Critical / Major）はゼロ。` + **何が良い修正か**を具体1文で褒める + 「残る指摘は運用確認/任意の品質改善/文書鮮度で、リリースを止める性質ではありません」。
   - ブロッカーあり: 見出し `## 総合（NO-GO）` + 本文 `**総合判定: NO-GO**（Critical n / Major n / Minor n）。` + 真因に対し修正方針が正しい旨と、止める理由 1 文。
   - 再レビュー時: 見出し `## 総合（GO）` とし、本文で前回ブロッカーが解消コミット SHA で潰れたことを明記。

4. **要否ラベルの凡例**（actionable な指摘が 1 件でもある場合に置く）:
   `各指摘に要否ラベルを付けています（MUST=要修正 / IMO=推奨・任意 / NITS=些細・任意 / Q=要確認 / FYI=対応不要）。`

5. **色付き絵文字＋ラベルの節見出し**（ラベル趣旨ごとにグルーピング・下記の固定順・該当するものだけ）:
   - `## 🔴 MUST（要修正） — <平文で何が起きるか>`
   - `## 🟡 IMO（推奨・任意） — …`
   - `## 🔵 Q（要確認） — …`
   - `## ⚪ NITS — …`
   - `## 🟢 良かった点` / `## 🟢 FYI（対応不要）`
   - 解消済み再掲は `### 🟢 解消済み（前回 🔴 MUST） — …`
   各節の中身は必ず ①`file:line` ②主語・述語のある平文（何が・どこで・どうなる） ③**対応**（任意なら「任意・著者判断」と明記）。
   - **同じラベルの指摘は必ず 1 つの節に集約する**。ラベルをまたいで交互に並べたり（例: Q → IMO → Q）、同一ラベルを別ラベルを挟んで 2 箇所に分割したりしない。節の並びは必ず `🔴 MUST → 🟡 IMO → 🔵 Q → ⚪ NITS → 🟢 FYI/良かった点` の固定順。同一ラベル節内は最も重大／到達性の高いものを先頭に。1 つのラベルに指摘が多いときは節内を箇条書きにする（節自体を割らない）。

6. **締め**: GO なら `Approve します。お疲れさまでした 🙏`。

## 必守ルール

- **コメント 1 行目に PR 作者へのメンション `@<GitHub ID>` を必ず置く**（`gh pr view <N> --json author -q .author.login` で取得。メンション無し投稿は差し戻し対象・2026-07-23 閣下指示）。
- **噛み砕き文体が正式（2026-07-13 閣下指示 → 2026-07-15 昇格・恒久）**: 「専門文体の正式版」と「噛み砕き版」を分けない。**投稿するのは噛み砕き文体そのもの**である。指摘の本文は、専門用語を圧縮して並べる書き方をやめ、主語・述語のある短い日常語の文で「何が起きるか → なぜ → どう直すか」の順に言い切る。具体則: ①指摘の見出しは症状を平文で（「〜が、…できない/してしまう」形。内部用語の羅列にしない）②専門用語・略語は必要最小限にし、使うときは中身を平文で併記（例: 実行ロール（= この Lambda に与える権限の束）／要件 REL-3「emit 失敗は自然回復を壊さない」）③短いたとえは 1 指摘に 1 つまで可（例: 「玄関に鍵をかけたのに勝手口が開いている」）④`file:line`・コミット SHA・「検証済み/未検証/推測込み」の epistemic honesty 表記は噛み砕いても省かない。1 指摘の本文は要点 3〜5 文＋箇条書きを目安にし、検証の詳細・経緯はレビューレポート側へ残して本文には書かない。書き上げたら「レビュイーが前提知識ゼロでこの節だけ読んで直せるか」で 1 回見直す。実例（この文体の抽出元・お手本）: 過去レビューの実例の approve コメント本文。
- **良かった点（🟢）を必ず 1 節入れる**。ダメ出しだけで終えない。
- **節見出しは「絵文字＋ラベル＋（要否）＋ — 平文テーマ」を必ず付ける**。`### IMO` のような裸見出し、`凡例:` で始まる自己流の凡例、絵文字なしの独自見出しは禁止（この体裁差し戻しの実例 2026-07-08 過去レビューの実例）。凡例は必守ルールの定型文をそのまま使う。
- **締めは `Approve します。お疲れさまでした 🙏` を定型で使う**（`Approve します 🙆‍♂️` 等の自己流に崩さない）。
- **総合の見出しに判定を括弧で入れる**（`## 総合（LGTM）` / `## 総合（NO-GO）`）。裸の `## 総合` にしない（結論を一目で出す＝差し戻し実例 2026-07-08 過去レビューの実例）。
- **既存事項は「既存事項・本 PR 非由来」と明記し、ブロッカーにしない**（base を `git show <base>:<path>` で確認してから severity 確定＝epistemic-honesty の severity ゲート）。他人の PR の近所にある既存バグを PR 由来のように MUST 付けしない。
- **絵文字は判定・各節見出しに付ける**（🔴🟡🔵⚪🟢）。無味乾燥な見出しにしない。
- **ラベルは趣旨ごとに 1 節へ集約し、`MUST → IMO → Q → NITS → FYI` の固定順で並べる**。ラベルをまたいで交互配置・同一ラベルの分割をしない（`Q → IMO → Q` になっていた差し戻し実例 2026-07-10 過去レビューの実例）。
- 内部コードネーム/ID を単独で論点に使わない（平文＋`file:line` が主・ラベルは括弧のトレース補助）。
- 重大度を過大に付けたら**訂正記録**を残す（例: 「先に NO-GO としたが 4 件は文書整合でマージを止める重大度でなかったため GO に訂正」）。
- 投稿は承認後のみ（他人 PR の GitHub 書き込みは承認ゲート・CLAUDE.md「他人の PR をレビューするとき」参照）。

## 最小テンプレ（クリーン GO の例）

```markdown
@<作者の GitHub ID>
差分を読み、挙動の正しさを一次情報（実コード・schema・repository）で追いました。

## 総合（LGTM）
**コードは LGTM 相当（GO）** です。要修正（Critical / Major）はゼロ。<この PR の一番良い所を具体1文>。残る指摘はリリースを止める性質ではありません。

## 🟢 良かった点
- <file:line + 平文で何が良いか>

Approve します。お疲れさまでした 🙏
```

## 完全例（IMO/Q/NITS/FYI/良かった点あり GO・見出しをこのまま真似る）

```markdown
@<作者の GitHub ID>
差分を読み、挙動の正しさを一次情報（実コード・schema・base ブランチ `git show`）で追いました。他人の PR のため破壊的リファクタ提案は出しません。

## 総合（LGTM）
**コードは LGTM 相当（GO）** です。要修正（Critical / Major）はゼロ。<核心の修正が良い理由を具体1文>。残る指摘は運用確認・任意の品質改善で、リリースを止める性質ではありません。

各指摘に要否ラベルを付けています（MUST=要修正 / IMO=推奨・任意 / NITS=些細・任意 / Q=要確認 / FYI=対応不要）。ブロッカー（MUST）はありません。

## 🟡 IMO（推奨・任意） — <平文で何が起きるか>
`path/to/file.tsx`（該当箇所）… <主語述語のある平文>。対応: 任意・著者判断。

## 🔵 Q（要確認） — <平文テーマ>
`path/to/file.tsx` … <確認したいこと>。対応: 確認のみ。

## ⚪ NITS — <平文テーマ>
`path/to/file.ts` … <些細な改善>。対応: 任意。

## 🟢 FYI（対応不要・既存事項/本 PR 非由来） — <平文テーマ>
`path/to/file.tsx` … base を `git show <base>:<path>` で確認済み。既存挙動で本 PR の回帰ではない旨を明記。

## 🟢 良かった点
- **<観点>**: <file:line + 平文で何が良いか>

補足（epistemic honesty）: テスト GREEN・ビルド成功が作者記載の自己申告なら「当方未実行（未検証）」と明記する。

Approve します。お疲れさまでした 🙏
```
