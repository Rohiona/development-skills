# レビュー指摘の重大度（severity）を断定する前に — 5点確認（正本）

> 発火条件: レビューで finding に **Major 以上**を付ける前に必ずこのファイルを読み、5点を一次情報で確認する。
> 経緯: 2026-07-22 ルールダイエットで `rules/common/epistemic-honesty.md` から全文退避（原文無改変）。
> スナップショット: `~/.claude/backups/rule-diet-20260722/`。

レビューで finding に **Major 以上**を付ける前に、機構が成立するかだけでなく、次の5点を一次情報（設計書 / コードコメント / コミット / 実コード / テスト）で確認してから severity を確定する。確認前の重大度は「推測」であり断定しない。

- **(a) 意図的でないか**: その挙動を設計判断・コメント・コミットが意図的に選んでいないか（例: 「retry は二重実行を招くので敢えて乗せない」が設計意図なら、それは bug でなく確認事項）。
- **(b) 本番で到達するか**: その経路が production で現実に発火するか（mock 前提・到達不能シナリオ・dev 専用スクリプトでないか）。
- **(c) test / prod の区別**: 欠陥が production コードか、テスト fixture か（test-only かつ初回実行で自己顕在化するなら Major ではない）。
- **(d) この diff 由来か既存か**: base（変更前）を実際に読み（`git show <base>:<path>` 等）、その欠陥が **base に既にあったか**を確認する。① この変更が**導入・悪化・顕在化**させた（守っていたガードを外した / 意味を変えて潜在バグが発火する等）なら Major を維持する。② **既存**かつこの変更で**悪化していない**なら PR のブロッカーにはしない（severity を下げる）が、**黙って落とさず**「既存事項・別 issue 候補」として base の該当 file:line 付きで記録に残す。他人の PR に「diff の近所にある既存バグ」を PR 由来のように Major 付けすると言いがかりになる。
- **(e) 修正が PR のスコープ内で完結するか**: 機構が実在（confirmed 相当）でも、根本原因が**リポジトリ全体に波及する構造**（deploy パイプラインの順序・共有基盤・同種の全 PR に共通する前提 等）にあり、ついで修正すると PR のスコープが膨れるものは、**MUST/Major（ブロッカー）にしない**。「**別 issue の起票を推奨**」を添えて **IMO（推奨・任意）へ落とす**のが既定。その PR 固有の運用手当て（既存 runbook の実行確認等）で足りる場合は Q（要確認）でもよい。（採用経緯: 過去レビューの実例 再レビューで unified deploy の「Lambda が migration より先」構造を MUST にしかけ、閣下の指摘で降格。2026-07-14）

「dead code」「未使用」「壊れる」等の断定も同様に、実コードの参照（Serena `find_referencing_symbols` / LSP）で**使用されていないこと**を確認してから言う（推測の誤報を避ける）。
（PDCA 由来: friction「BUG-A/B を意図・到達性・test-prod 未確認のまま Major と断定→『本当にバグ?誤報では?意図的では?』と問われ訂正。isLambdaEnvironment を dead code と誤報（実際は使用中）」。2026-06-11）

## ⑥ 依存の実体・コメント適用範囲・必要前提の観測（2026-07-27 追加・過去レビューの実例 誤 confirmed 起点）

「stale」「参照が変わらない」「キャッシュが効かない」「二重発火」系を Major 以上と断定する前に:

- 依存値の**実体**（ラッパーか中身か・どの変数か）を特定し、生成元→更新経路→消費点を file:line で追ったか。
  ラッパーオブジェクトと中身（`.value` 等）は別の値として区別する。
- コード内コメントを根拠に使うとき、そのコメントが指す変数と指摘対象の変数の**同一性**を確認したか（転用禁止）。
- 外部ライブラリの挙動が前提なら、lockfile でバージョンを特定のうえ配布物/公式 docs を実読したか。
- 指摘の成立に必要な前提（kill premise）を列挙し、**未確認の前提が残っていないか**。残るなら断定せず「未確認」とラベルする。

実例: 2026-07-26 過去レビューの実例 — ヘッダ固有の「参照不変」コメント（definition.value の話）をラッパー依存の useMemo へ転用して誤 confirmed（memory id 2108）。
