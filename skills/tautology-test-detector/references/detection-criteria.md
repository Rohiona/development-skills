# 検出 criteria（5 類型）と誤検出ガード

`SKILL.md` の判定段（フロー 2）で使う正本。各類型に〔定義 / 判別の決め手 / 実例 / 明白(自動対応可) or 議論あり(レポートのみ) / 書換方針〕を置く。
実例は過去レビューの実例（frontend テスト棚卸し 224→188 ファイル / API サーバーテスト棚卸し 78→71）で実際に削除/縮小されたテストに基づく。

---

## ① 純トートロジー（tautology）

- **定義**: assert している内容が実装から自動的に真になる。実装をコピペすれば必ず通る。リグレッションを捕まえない。
- **判別の決め手**: 「この assert は、実装にバグを入れたら落ちるか？」を問う。落ちないなら（＝実装と同義の言い換えなら）トートロジー。
- **実例**:
  - `src/temp/sum.test.ts`: `expect(sum(1,2)).toBe(3)`（`sum` は `a+b` を返すだけ）。Vitest 導入時のスキャフォールド残骸。
  - `expect(CONST).toBe(<CONST と同じ literal>)` のような定数の自己確認。
- **扱い**: **明白＝自動対応可**。特に `**/temp/**` 配下のスキャフォールドや「getting started」サンプル（`adds 1 + 2 to equal 3`）は議論の余地なし。
- **書換方針**: 基本は削除。もし対象関数に実際の分岐/エッジケースがあるなら、それを突く振る舞いテストへ書き換える（境界値・異常系）。

## ② source-grep メタテスト

- **定義**: production のソースコードを**文字列として**読み込み（`readFileSync` / `spawnSync('grep')`）、特定文字列の有無や個数を assert する。コードの**振る舞い**ではなく**書かれ方**を検査している。
- **判別の決め手**: assert 対象が「ソースの中身（文字列）」か。lint ルール・型チェックで等価に代替できるか。
- **実例**:
  - `no-as-any.test.ts`（54〜186 行規模の実例あり）: production を grep して `as any` 残存 0 を assert。→ Biome `noExplicitAny`（error 級）で代替可能。
  - `consumer-imports.test.ts` / `no-direct-rpc.test.ts`: ソースを読み `from '~/gen/connectrpc/...'` 直 import が無いことを assert。
  - `package-structure.test.ts`（192 行の実例）: `package.json` / CI yaml を文字列 grep。
- **扱い**:
  - **lint/型で完全代替済み**（例: `as any` ↔ `noExplicitAny` が有効）→ **明白＝自動対応可**。ただし**代替が現に有効なことを事実で確認してから**消す。
  - **lint 代替が存在しない規約**（アーキテクチャ規約等、対応する lint ルールが無い）→ **議論あり＝レポートのみ**。消すと検出経路が無くなる。lint ルール新設 or 維持を人に判断させる。
- **書換方針**: 削除し、必要なら「この規約は <Biome ルール名 / tsc> が担保」と代替を明記。代替が無いなら lint ルール化を提案。

## ③ 自己参照の循環メタ

- **定義**: テストが**自分自身のファイル**やテストファイル群を読んで assert する。最も無価値（テストがテスト自身の存在/内容を確認しているだけ）。
- **判別の決め手**: 読み込み対象が `__filename` / 自テストのパス / `*.test.ts` 自体か。
- **実例**: `openapi.route.test.ts` の一部 describe: 自ファイルを grep する完全循環メタとして describe ごと切除。
- **扱い**: **明白＝自動対応可**。
- **書換方針**: 削除。

## ④ mock-only zero-value contract test

- **定義**: `vi.mock` 等で**被検対象そのもの**を丸ごと置換し、その後 mock の戻り値や呼ばれ方だけを確認する。本物のコードは 1 行も実行されないので、wiring 保証は実質ゼロ。
- **判別の決め手**: 「mock を剥がしたら、このテストは何を検証しているか？」を問う。何も残らないなら zero-value。**被検対象 = mock 対象**になっていないか。
- **実例**: 過去レビューの実例の listing page 7 件（`XxxList` 系の一覧ページコンポーネント群）: `vi.mock` で `ListLayout` を完全置換した上で mock の挙動を確認 → page 固有の `it` がゼロなものは削除、固有 `it`（I-001/I-002 等）があるものは縮小して残した。
- **扱い**: **ほぼレポート（要 LLM 判定）**。mock が「外部依存の遮断」なのか「被検対象の置換」なのかは実コードを読まないと分からない。被検対象の置換が確実で固有 assert がゼロのときだけ明白扱い。
- **書換方針**: 被検対象は mock せず実物を動かす形へ。同等のカバレッジが別テスト（例: コンポーネント単体テスト）にあるなら重複削除。固有 `it` は残す。

## ⑤ doc / コメント存在チェック

- **定義**: 設計ドキュメントやコメント文字列が「存在するか」を assert する。
- **判別の決め手**: assert 対象がコメント/ドキュメントのテキストか。
- **実例**: 「自分で書いたドキュメントが存在しているか」を確認するだけのテスト（過去レビューの実例で調査の起点になった anti-pattern）。
- **扱い**: **レポート**（多くは削除妥当だが、ドキュメント生成・spec 整合の意図がある場合があるので人に確認）。
- **書換方針**: 削除。ドキュメント整合を本当に守りたいなら spec 生成側のチェックへ移す。

## 誤検出ガード（消してはいけないもの）

静的プレフィルタや類型の見た目に**一致しても価値がある**テスト。これらを「メタ/トートロジー」と誤判定して消すと回帰検知を失う。過去レビューの実例のトリアージで実際に「撤回（消さない）」と判断されたものを反映する。

| 見た目 | 実体 | なぜ残す |
|---|---|---|
| ソースや型を読んでいる | **実行時 wiring 検証**（`instanceof` / DI コンテナ解決 / repository 配線） | ソースを文字列で読むのではなく**実行して**配線を確かめている。例: `dependencies.test.ts` の 14 repository × `instanceof` チェック（過去レビューの実例で削除提案を撤回＝維持） |
| フラグ分岐の重複・移行用 | **移行期の temp smoke**（移行用フィーチャーフラグ系 / 旧→新並行運用） | 移行完了で一括除去される設計。期間限定で有効。重複は temp/permanent 同居期の必然 |
| 同名の `it` が並ぶ | **各 field validator の網羅** | 同一ファイル内で各バリデータを同名 `it` で検証する正当な重複 |
| `*.snapshot.test.ts` | **誤命名だが本物の hook 挙動テスト**（`toMatchSnapshot` を使っていない） | 名前に反して実際の振る舞いを検証している。リネーム提案は過去レビューの実例で撤回 |
| `onSuccess`/`onError` の sentinel | hook wrapper の最小配線確認 | 薄いが wiring の最低保証 |
| 単純な `expect(x).toBe(y)` | **境界値・異常系の振る舞い検証** | 実装にバグを入れたら落ちる＝価値あり。単純さは無価値の証拠ではない |

**鉄則**: 「ソースを*読む*」=メタの疑い、「コードを*実行する*」=正当、で一次切り分け。判断が割れたら**消さずレポート**。
