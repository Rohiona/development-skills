# tautology-test-detector 学習観点集（learned-lenses）

`tautology-test-detector` が **5 類型（SKILL.md）に上乗せして読む学習観点**。
SKILL.md / `detection-criteria.md` が安定 core、ここは
**人間レビュアーの「このテストは何も検証していない」系の指摘から蒸留して育つ層**
（`/hahifuhe:review-retro` が追記する）。

各観点は **観点（どんな無価値テストか）/ 範囲（どこに出るか）/ 検出（どう見分けるか）/ 誤検出ガード（消してはいけない隣接物）** で持つ。

- 過去傾向を**蒸留した有界な観点**。フロー中の adjudicate でこの集合も併読する（コンテキスト一定）。
- **上限の目安 10 観点**。超過 or 定期で**統合**（近接マージ・陳腐化剪定・安定したものは `detection-criteria.md` へ昇格）。
- 生のケース履歴は `~/.claude/agents/hahifuhe-review.cases.jsonl`（`reviewer:"tautology"`）に退避。**ここには溜めない**。
- severity 既定は **Minor**（GO/NO-GO の数式は変えない。SKILL.md「重大度と GO/NO-GO」準拠）。
- 初版は空。retro を回すまでは 5 類型のみで動く。

### T1. env・共通 mock の「既定値」が被検分岐を片側に固定していないか（緑だが分岐は 0 回実行）

- **観点**: テストは通っているが、被検コードの分岐条件を決める入力が **env の未設定 fallback** や **共通 mock の既定戻り値**で片側に固定され、対象ロジックが一度も実行されていないテスト。「ファイルは存在しテストも緑」なので、カバレッジを口頭で確認すると見落とす。
- **範囲**: 被検モジュールが `process.env.X` を分岐条件に使う場合（`const URL = process.env.X || 'http://localhost:...'` 形式が典型）、および `beforeEach` の共通 mock が空配列・空オブジェクト・null を既定で返し、その戻り値が被検関数内の合流・整列・種別分岐の入力になっている場合。
- **検出**: ①被検コードの分岐条件（`startsWith('https://')`・`if (list.length)`・種別 switch 等）を列挙し、テスト側でその条件を反転させる入力が **1 ケースでも作られているか**を数える。②共通 mock の既定が `[]`/`{}` なら、その戻り値を消費する分岐は全滅を疑う。③決定打は破壊対偶: 当該分岐の実装を壊しても既存テストが緑のままなら未到達確定。
- **誤検出ガード**: 分岐の片側だけを意図的に固定し、反対側を別ファイル（integration/smoke）で担保している構成は健全。消す前に反対側の担保先を探す。移行元にテストが無かった新規コードは「縮退」ではないので T2 と混同しない。

### T2. 移行・リファクタでテストの「存在」だけ確認し、ケース数と意味論の縮退を見逃していないか

- **観点**: 移行元のテストを削除し移行先に同名・同趣旨のテストを置いたとき、**ファイルは揃っているがケース数・検証している意味論が痩せている**（例: 16 ケース → 2 ケース、境界値・null/空文字・特殊文字・混在ケースが落ちる）。実装が 1:1 移植なら現時点の挙動退行は 0 でも、**将来の退行に対する検知力だけが失われる**。
- **範囲**: 大規模移行・ディレクトリ移設・パッケージ切り出しを含む PR。特に「代替カバレッジは移行先に存在する」と主張されている箇所。移行先にテストファイルが**存在しない**モジュール（消失）も同じ観点で拾う。
- **検出**: 削除された `*.test.ts` と移行先テストを **`it`/`test` のケース数と各ケース名で 1:1 対応表にする**。ファイル存在の確認で止めない。対応表に欠けたケースが、移行先の他ファイル（integration/regression）で担保されているかまで追い、無ければ縮退として報告する。
- **誤検出ガード**: 意図的な重複排除（移行元が同じ分岐を複数ケースで重ねて叩いていた等）は縮退ではない。設計書・PR 本文に `intentionally_omitted` 相当の記録があるものは対象外。

### T3. そのテストは CI で実際に実行されるか（実行されないテストを「代替カバレッジがある」根拠に使わない）

- **観点**: テストの中身が健全でも、**jest config の `testPathIgnorePatterns`・ディレクトリ配置規約（`/integration/` `/smoke/` `/regression/` 配下）・package の CI スクリプトが typecheck のみ**といった理由で CI から除外されていると、退行はマージ後まで誰も検知しない。レビューで「代替のテストが同 PR 内にある」と安心材料にする前に、そのテストが CI 実行対象かを必ず確認する。
- **範囲**: カバレッジの担保根拠として持ち出す全テスト。特に「DB 不要なのに `/integration/` 配下」「契約を pin する唯一のテストが、CI では型チェックしか回さないパッケージにある」構成。
- **検出**: 担保根拠にするテストのパスを、①該当パッケージの jest config の `testPathIgnorePatterns` / `testMatch`、②CI ワークフローが呼ぶ package.json スクリプトの実体（`test` か `check-types` か）と突き合わせる。設計書・テスト計画に「CI 非実行」相当の自己申告があればそれも一次資料として拾う。
- **誤検出ガード**: ローカル手動ゲートとしてリリース/マイルストーンの完了条件に組み込まれている等、CI 非実行が意図的で運用に組み込まれているものは「除外の事実を明記」に留め、欠陥として断定しない。
