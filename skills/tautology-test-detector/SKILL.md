# tautology-test-detector

「テストが green でも、実は何も検証していない」テストを能動的に見つけ出す規律。トートロジー・メタテスト・mock-only の 3 系統を中心に、`*.test.ts` / `*.spec.tsx` 等のテストコードを対象にする。

## このスキルの本質

テストは「実装とは独立に、観測可能な振る舞いを検証する」から価値がある。ところが AI も人も、量産の過程で **実装をそのまま言い換えただけのテスト**や、**ソースを文字列として grep して規約を assert するテスト**を平気で混ぜ込む。これらは green になるが、実装をコピペした瞬間に通ってしまい、リグレッションを 1 つも捕まえない。しかも「設計書に準じたテストを書いた」と説明されるとレビューを通過しやすく、静かに蓄積してテスト時間とメンテコストだけを食う。

このスキルの主役は **「このテストは振る舞いを検証しているか、それとも実装の言い換えか」を、テストを書いた側が能動的に問い直すこと**。指示されてからではなく、テストを書き終えた仕上げのターンで自分から発火させる。

> 重要な前提: トートロジー判定は誤りうる。**「消す」より「疑わしきはレポートして人に渡す」を既定**にし、自動で消すのは議論の余地がない明白な分だけに限定する。`references/detection-criteria.md` の誤検出ガードを必ず併読する。

## いつ発火するか（能動が主）

- **テストを書き終えた直後** — コミット前・報告前に、自分が書いたテストを一度この観点で点検するターンとして
- **`extract-testable-module` などの実装系スキルの仕上げ** — 切り出し後に書いたテストの健全性ゲートとして
- **PR レビューでテストの健全性を見るとき** — `hahifuhe:review-all` の Phase 2 から read-only で起動される（後述）
- **明示的な依頼** — 「無意味なテスト/トートロジー/メタテストを探して」「テストを棚卸し/掃除して」など

## 何を検出するか（5 類型）

詳細な定義・実例・書換方針・「明白(自動対応可)か議論あり(レポートのみ)か」は `references/detection-criteria.md` に置く。要約:

| # | 類型 | 一言で | 既定の扱い |
|---|---|---|---|
| ① | 純トートロジー | 実装をそのまま言い換えた自明な等値。スキャフォールド残骸 | 明白なら自動対応可 |
| ② | source-grep メタ | production ソースを文字列として読み、`as any` 残存等を assert（lint/型で代替すべき） | lint で代替済みなら自動対応可 / 代替が無い規約はレポート |
| ③ | 自己参照の循環メタ | 自分自身やテストファイルを grep して assert | 明白なら自動対応可 |
| ④ | mock-only zero-value | `vi.mock` 等で被検対象を丸ごと置換し、mock の挙動だけ確認 | ほぼレポート（要 LLM 判定） |
| ⑤ | doc/コメント存在チェック | ドキュメントやコメント文字列の存在を assert | レポート |

## 消してはいけないもの（誤検出ガード）

見た目が似ていても**価値のあるテスト**がある。これらを消すと回帰検知を失う。詳細は `references/detection-criteria.md`：

- **実行時 wiring 検証** — `instanceof` / DI コンテナ解決 / ルーティング配線など「実際に動かして配線を確かめる」テスト。ソースを読むのではなく実行する。
- **移行期の temp smoke** — フラグ切替や旧→新の並行運用を守る期間限定テスト（移行完了で消える設計）。
- **同一ファイル内の同名 it** — 各 field validator を同じ名前の `it` で並べる等、網羅のための正当な重複。
- **誤命名だが本物** — `*.snapshot.test.ts` でも `toMatchSnapshot` を使わず実際の hook 挙動を検証しているもの。
- **振る舞いを検証する本物** — 入力→出力・副作用・例外を検証しているテストは、たとえ単純でも対象外。

## 検出フロー（3 段）

### 1. 静的プレフィルタ（候補抽出・決定的）

`scripts/prefilter.sh` を実行し、テストファイルから候補行を機械的に surface する。判定はしない。

```bash
# 範囲を絞って実行（PR レビューなら diff のテストファイルに限定）
bash ~/.claude/skills/tautology-test-detector/scripts/prefilter.sh apps/frontend/src
bash ~/.claude/skills/tautology-test-detector/scripts/prefilter.sh \
  $(git diff --name-only develop...HEAD | grep -E '\.(test|spec)\.tsx?$')
```

出力は `category<TAB>file:line:match` の候補リスト。パターンと誤検出帯域は `references/static-prefilter.md`。

### 2. LLM 判定（adjudicate）

候補を 1 件ずつ `references/detection-criteria.md` の類型定義と**誤検出ガード**（および `references/learned-lenses.md` の学習観点があれば併せて）に照らして判定する。テキスト grep では区別できない「メタか実行時 wiring か」「mock-only か正当な単体か」はここで実コードを読んで決める。コード探索はプロジェクト方針に従い **Serena 既定 / 型・参照は LSP**（`code-navigation` ルール）。

各候補に **事実／推論／推測**のラベルを付ける（`epistemic-honesty` ルール）：
- 事実 = テスト本文と被検対象の実装を読んで確認（file:line 併記）
- 推論 = 確認した事実から「これは振る舞いを検証していない」と導いた（前提を明示）
- 推測 = 読み切れず判断保留（「要確認」と明記）

### 3. レポート / 対応

- **既定はレポート**: 候補ごとに〔類型・場所・なぜ無価値か（or 価値があるので除外）・書換 or 削除の方針〕を一覧で返す。最終判断は人。
- **明白分のみ対応可**: 議論の余地がないもの（純トートロジーのスキャフォールド、自己参照の循環メタ、lint で完全代替済みの source-grep）に限り、削除または振る舞いテストへの書換を実施してよい。**判断が割れうるものは絶対に自動で消さない。**
- 代替が消えることへの言及を必ず添える（例: 「この `as any` grep を消すなら、Biome `noExplicitAny` が error 級で有効なことを確認した上で」）。

## 重大度と GO/NO-GO

トートロジー/メタテストは**リリースを止める瑕疵ではない**（振る舞いの誤りではなく、無価値資産の蓄積）。`hahifuhe:review-all` に組み込む際の既定 severity は **Minor**。したがって GO 判定（Critical=0 かつ Major=0）の数式は変えない。例外的に Major 相当に上げるのは「そのテストの存在が**有効なテストの不在を偽装している**」と判断できる場合のみ（例: 唯一のカバレッジに見えて実は mock-only zero-value で、本物の検証が 0 件）。

## やってはいけないこと

- **疑わしきを自動削除** — 判断が割れうるものを消す。本スキル最大の事故。レポートに回す。
- **lint/型の代替を確認せず source-grep を消す** — 規約検出経路が消滅する。代替の存在を事実で確認してから。
- **実行時 wiring を「メタ」と誤判定** — ソースを読むテストと実行して配線を確かめるテストは別物。
- **対象拡大** — テストコード以外（production・設定）に手を出さない。振る舞い変更も混ぜない。
- **未実行での「掃除しました」** — 削除/書換をしたら型チェックとテストを走らせ green を確認する。
