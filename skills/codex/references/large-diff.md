# 巨大 diff / 長時間実行への対処

Codex は 1 セッションで処理できる diff に限界がある。`git show --stat` で概算し、下記目安を超えるなら**必ず絞り込む or 分割**する。

デフォルトの `timeout` は 1200（20 分）。下記目安もこれを基準に記述する。

## 規模別目安表

| 対象の規模 | 所要時間目安 | 対処 |
|---|---|---|
| ~500 行 / ~10 ファイル | 約 3〜5 分 | そのまま 1 回で OK（`timeout 1200` のまま） |
| 500〜3000 行 / 10〜30 ファイル | 約 10〜15 分 | レビュー観点を絞る + ファイル優先順リストを inline 指示（`timeout 1200`） |
| 3000 行超 / 30 ファイル超 | 完走しない可能性大 | **絶対にそのまま投げない**。下記で分割 |
| 巨大マージ（100+ ファイル / 万行級） | `timeout 1200` でも不完走する想定 | **ユーザーに絞り込み合意を取ってから呼ぶ** |

## ユーザー指示が巨大対象の時の振る舞い

「develop 最新 commit を見て」のような **単数形指示** でも、対象が巨大マージコミットなら**そのまま投げずに分割提案を先に出す**。empirical iter 3 で分割判断に subagent が迷って retries を増やした実績あり。例:

> 「対象は 1645 ファイルの巨大マージです。そのまま投げると完走せず `-o` も空のままになります。以下のいずれかで進めたいですが、どれにしますか？ A: 特定アプリ（例: API サーバー）に絞る / B: 認証関連に絞る / C: マージ内の個別 commit を 1 つずつ」

## 分割パターン

1. **優先カテゴリ別に複数 Codex 呼び出し**: 認証関連 / DB schema / API 互換 を別セッションで並列実行
2. **マージコミット内の個別 commit を 1 つずつレビュー**: `git log <merge>^1..<merge>^2 --oneline` で列挙、重要なものだけ `git show <sha>` で Codex に渡す
3. **Claude 側で先に `git show --stat` + 重要ファイル抽出を済ませてから Codex に渡す**: 「このファイルだけ見て」と範囲指定する

## 巨大 diff を丸投げすると起きること（iter 3 実測）

- Codex が数時間走り続ける（S1 で 6.7 時間）
- タイムアウト中断時に `-o` ファイルが**完全に空 or 未生成**で回収不能（`-o` は Codex が最終メッセージを正常に出したときだけ書き出される。タイムアウト（exit 124）では書かれないと見るべき）
- stdout 末尾の tail 取得にフォールバックせざるを得なくなる
- session ID も失われ、継続議論（`codex exec resume`）が不可能になる

## タイムアウト対策

- `-o` を指定しつつ、同時に stdout もログに取る: `codex exec ... -o out.md </dev/null 2>&1 | tee /tmp/codex.log`（タイムアウト時は log から回収）
- Bash 側で必ず `timeout <秒数>` を付ける（Codex 自身では止まらない、デフォルト 1200）
- `</dev/null` で stdin を閉じる（忘れると「Reading additional input from stdin...」で固まる）
- 1 Codex 当たり 20 分以内を目安。超える規模は分割
