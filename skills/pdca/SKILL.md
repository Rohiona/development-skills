# PDCA 自己改善ループ（対話型・GitHub なし・効果検証つき）

目的は「Claude 自身の作業ログを読み返し、問題候補を**多めに**挙げ、**本当に問題かは人間が選択で確定**し、採用した分だけ改善に落とし、**その改善が効いたかを縦断的に検証**して、効かなければ直し直す」こと。

PDCA との対応:
- **C (Check)** = フェーズ0（毎回の冒頭で前回までの改善の効果を確認）
- **P (Plan)** = フェーズ1〜4（発見→取捨選択→深掘り→議論）
- **D (Do)** = フェーズ5（反映）
- **A (Act)** = Check の結果に応じて「定着」or「再改善に戻す」

## 鉄則（崩すと意味がなくなる）

- **AI は問題かどうかを決めつけない**: シグナル ≠ 問題。検出は多めに出すが「問題かどうか」の確定は必ず人間の選択（フェーズ2）に委ねる。中断・拒否などのシグナルは意図がないことも多い（誤検出前提）。
- **効果は「証明」でなく「弱い証拠の積み上げ」**: LLM は非決定的でタスクも毎回違うため、改善の因果を厳密に証明はできない。狙うのは「再発が減った／成功条件を満たした」という弱い証拠の蓄積。盛らない。
- **合意前に自動で書き換えない**: SKILL.md / CLAUDE.md / `~/.claude/rules/` / 各種スキルを、議論で合意する前に編集しない。
- **GitHub に登録しない**: 記録はローカルの `.claude/pdca-logs/` のみ。
- **事実・推論・推測を分ける**: ログにも提示にも、transcript で確認できた事実／推論／裏付けのない推測を必ずラベルで区別する（epistemic-honesty 準拠）。
- **短く閉じる**: 1候補＝数行。digest 全文の貼り直しはしない。

## パイプライン

```
0. Check    過去の「反映済み」改善を読み、今セッションで再発がないか/成功条件を満たしたかを照合（A: 定着 or 再改善）
1. 発見      二系統で問題候補を「多めに」洗い出す（過剰検出OK）
              ├ 1a 直近セッション (extract-session.sh)
              └ 1b 横断 friction  (read-insights-friction.sh = insights facets。古ければ /insights 実行を訴求)
2. 取捨選択  まとめてチェック式で、人間が「問題だと思うもの」を選ぶ（選ばれない=問題でない）
3. 深掘り提案 採用された問題だけ、原因を再検討し「予想できる効果」を提案ベースで提示
4. 議論      それをもとにユーザーと議論
5. 反映      合意分を改善に落とす。★必ず「カテゴリ」と「観測可能な成功条件」を付ける
```

---

### フェーズ0: Check（前回までの改善の効果を確認）★最初に行う

**前提（順序）**: 照合には今セッションの digest が要る。なので **先にフェーズ1a の `extract-session.sh` を実行して digest を取得してから**、本フェーズを行う（Check は概念上は先頭だが、入力として 1a digest を使う）。

`.claude/pdca-logs/` の**全**過去ファイルを読み、ステータスが `反映済み(観測中)` の項目を集める。各項目には「カテゴリ」と「成功条件」があるはず。1a digest と照合して効果を判定する:

- **再発した**（同じカテゴリの問題が今セッションでも起きた）→ その項目の観測ログに `×（再発: <日付>）` を追記し、判定を `効果不十分(再発→再改善へ)` に。**Act**: フェーズ2以降で再改善候補として扱う。
- **成功条件を満たした**（その状況が今回あり、条件どおり振る舞えた）→ 観測ログに `○（<日付>）` を追記。`○` が一定回数（既定3回）連続したら判定を `定着` に。連続の**カウント単位は「/pdca 実行1回＝観測機会1回」**（暦日でもセッション数でもない）。
  - 補足: 成功条件が「〜しない」型（不在の確認。例「digest にメタ注入が出ない」）の場合、**その状況は毎セッション必ず到来する**とみなし、条件を満たせば ○ を付けてよい。「状況が来たか不明」な保留は、条件が特定操作の発生を前提とする型に限る。
- **該当状況が来ていない**（判定材料なし）→ 何もしない（「再発なし＝効果ありとは限らない」を踏まえ、無理に○にしない）。

**観測ログの書き込み先（重要）**: ×/○ の追記とステータス更新は、**その項目が元々書かれている過去日付のファイルを直接編集して育てる**（今日のファイルに新規コピーを作らない）。今日の `<日付>.md` は「今回新たに発見した候補」用。なお pdca-logs への記録は鉄則「合意前に自動で書き換えない」の対象外（対象は SKILL.md / CLAUDE.md / rules / スキル本体）なので、Check の観測更新は合意不要で行ってよい。

Check の結果は冒頭で簡潔に報告する（例: 「前回の改善A、今回も成功条件を満たし2/3。改善Bは再発、再改善候補に回します」）。観測対象が無ければ「検証対象なし」とだけ言う。

### フェーズ1: 発見（多めに・二系統）

発見ソースは **常に2つ併用**する。鮮度の高い「直近セッション」と、過去横断の「insights friction」。

#### 1a. 直近セッション（鮮度）

```bash
~/.claude/skills/pdca/scripts/extract-session.sh
```

- 引数なしで今のプロジェクトの最新 transcript（＝通常このセッション）を読む。特定セッションは `extract-session.sh <session-id>`。
- 出力は「Human turns」「Tool errors / rejections」の2ブロック。

#### 1b. 横断 friction（過去全体・insights 由来）

```bash
~/.claude/skills/pdca/scripts/read-insights-friction.sh
```

- `/insights` が生成した永続ファイル（`~/.claude/usage-data/facets/*.json`）から、friction を含むセッションを抽出する。**insights 自体は起動しない**（スキルからは起動不可。検証済みの事実）。あくまで過去に生成されたキャッシュを読むだけ。
- 出力冒頭に `last_insights:`（前回実行時刻）と `stale_sessions_since: N`（以降の未分析セッション数）が出る。
- **★訴求ターン（必須）**: facets は `/insights` を打たないと最新化されない。次の基準でユーザーに訴求する:
  - `status: NO_DATA`（insights 未実行）→「横断分析の元データがありません。`/insights` を一度実行してから `/pdca` を再開すると、過去横断の friction も棚卸しできます」と案内し、今回は 1a のみで進める。
  - `stale_sessions_since` が大きい（目安 **10 以上**）→「前回 insights から N セッション未分析です。最新化するなら一度 `/insights` を実行してください。このまま既存データで進めることもできます」と訴求（**強制しない＝ソフト訴求**）。ユーザーが続行を選べば既存 facets で進める。
  - 小さい（目安 10 未満）→ 一言添えるだけで続行。
- **私からは `/insights` を起動できない**ので、必ず「ユーザーが実行 → /pdca 再開」という導線で促すこと。勝手に起動を試みない。

#### 候補の作り方

1a の digest と 1b の friction を合わせて、**問題候補を多めに**挙げる。

- 1b は34件規模になりうるので、**生のまま全部出さず、テーマにクラスタリングしてから**出す（insights の friction_analysis 相当を都度やる）。例:「スコープ誤読」「対象アーティファクト取り違え」「未検証の主張」等の塊にまとめ、各テーマに代表例を添える。
- 1b の friction_detail は insights の**推論**（LLM要約）なので「事実」でなく**候補（推論ソース）**として扱う。確定は取捨選択フェーズの人間に委ねる。
- スクリプトのシグナルに縛られず自分の振る舞いも自己批判的に洗う（修正指示・繰り返し・中断/拒否・空回り・過剰な確認・段取りミス・出力品質 等）。迷ったら候補に入れる。
- 本当に1つも無ければ「今回は候補なし」と正直に報告して終了。

### フェーズ2: 取捨選択（まとめてチェック式）

候補を **AskUserQuestion の multiSelect** で提示し、人間に「問題だと思うもの」を選ばせる。

- 1問の選択肢に候補を列挙（各候補は短い1行タイトル）。**選ばれなかった候補＝問題でない**。
- AskUserQuestion は1回で最大4問・各2〜4択。候補が4件を超えるときは複数問に分割（例: 4件ずつ）。多すぎる場合は重要度の高い順に絞り、その旨を伝える。
- フェーズ0で「再発」した項目があれば、ここに「再改善候補」として混ぜて選ばせてよい。

### フェーズ3: 深掘り提案（予想効果つき）

「問題」に選ばれた候補だけを対象に、提案ベースで深掘り。1件ずつ:

- **原因の再検討**: 事実を根拠に再評価（推論/推測ラベル付き）。
- **改善案**: どの改善先（新規スキル / 既存スキル / CLAUDE.md / rules）に、どう反映する案か。
- **予想できる効果**: 何が良くなるか。薄い/コスト高なら正直にそう言う。

### フェーズ4: 議論

深掘り提案をもとにユーザーと議論。決めつけず、ユーザーの判断で採否・方針を確定する。

### フェーズ5: 反映（合意できたものだけ）

合意できた改善だけを適切な改善先に落とす（**改善先は何でもあり**）:

- 再現性のある手順 → **新規スキル化**（`skill-creator` を使ってよい）
- 既存スキルの不足・曖昧さ → **既存 SKILL.md の改修**
- 横断的な原則 → **CLAUDE.md / `~/.claude/rules/` の追記**

★反映時に**必ず**次の2つを決めてログに書く（これが無いと効果検証できない）:

1. **カテゴリ**: 再発照合に使う短いタグ（例: `探索フェーズの早すぎる構造化質問`）。
2. **成功条件**: 観測可能な形（例: 「次に探索フェーズが来たとき、多軸フォームを出さず散文で確認できたら○」）。

反映したらステータスを `反映済み(観測中)` にし、観測開始日を書く。

## ログ（.claude/pdca-logs/）

書き込み先は **実行中プロジェクトの `.claude/pdca-logs/<YYYY-MM-DD>.md`**（`date +%F`）。同日ファイルがあれば追記。

1候補のフォーマット（発見〜反映で育てていく）:

```markdown
## <時刻 HH:MM> <一言タイトル>

- 事実: <transcript で確認できたこと。timestamp や発話を根拠に>
- 推論/推測: <原因の見立て。推測なら「推測」と明記>
- ステータス: 候補
<-- 問題採用後に追記 -->
- 改善案: <どう直すか>
- 予想効果: <何が良くなるか>
- 反映先: <file / 新規スキル名 など>
- カテゴリ: <再発照合タグ>
- 成功条件: <観測可能な合格条件>
- 観測: <日付 ○|×（再発/充足）を追記していく>
```

ステータス遷移:

```
候補 ─(フェーズ2)→ 問題 | 非問題(理由を1行)
問題 ─(フェーズ3-4)→ 検討中
検討中 ─(フェーズ5)→ 反映済み(観測中) | 見送り
反映済み(観測中) ─(フェーズ0 Check)→ 定着(○が既定3回) | 効果不十分(再発→再改善へ)
効果不十分(再発→再改善へ) ─(フェーズ2で再採用)→ 検討中（原因を変えて作り直す。前回と同じ改善を繰り返さない）
```

`非問題` には理由を1行添える（次回の誤検出抑制のヒントになる）。

## 出力スタイル

- 冒頭で Check 結果 → 各フェーズの境目を明示。
- 候補が多いときは件数と重要度順を伝える。
- 最後に保存先 `.claude/pdca-logs/<日付>.md` を明示する。
