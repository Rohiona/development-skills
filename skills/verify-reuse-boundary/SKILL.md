# verify-reuse-boundary

再利用・流用・同一視を「事実」として確定する前に、その**境界**が本当に成り立つかを一次情報で確かめる検証の規律。

## なぜ必要か

AI も人も、既存資産を前にすると「これと同じだろう」「これに乗せれば済む」と**楽観的に再利用境界を引く**引力に逆らえない。型・契約・エンドポイント・インフラのレールは、表層が似ていても実体が違うことが多い。未検証の「同じはず」を土台に設計や実装を積むと、その仮定が崩れた瞬間に積み上げた判断がまとめて倒れる——しかも倒れるのはたいてい下流（レビュー・実装・本番）で、手戻りが大きい。

このスキルの主役は **「同じはず」と口にした、その瞬間に手を止めて一次情報で確かめること**。指示されてからではなく、再利用・同一視を判断した時点で能動的に発火させる。検証して同一が確認できたものだけを「事実」として下流の判断材料にする。

## いつ発火するか（能動が主）

次のような判断・記述をした瞬間に発火する。最大の効き目は**設計（架構）フェーズ**——再利用境界はここで決定・断言され、ここで潰せば下流の手戻りがまとめて消える。要件で技術事実を主張するとき、実装で import / 流用するときにも発火する。

- 「既存の〇〇を再利用／拡張する」「〇〇に合わせるだけ」
- 「A と B は同じ（同型／同契約／同じ戻り値／同じエンドポイント／同じ権限）だから流用できる」
- 「この仕組み（キュー／worker／テーブル／状態ストア）に相乗りさせれば済む」
- 「差し替えるだけ」「フィールドを1つ変えるだけ」「同じ関数を呼べばいい」
- レビューで「同じだと思っていたが実は別物だった」系の指摘を繰り返し受けている
- 「これは（スキル/エージェント/CLI から）起動できない／その機能は存在しない」と、ツール・コマンド・機能の可否や存在を断定するとき（CLI の `--help`／公式 docs／設定ファイルの実読で確かめる）

## 何を「境界」として疑うか

再利用が破綻するのは、たいてい次のいずれかの境界で「同じはず」が外れるとき。判断対象がどの境界をまたぐかをまず特定する。

| 境界 | 「同じはず」が外れる典型 |
|---|---|
| 型 | DB レコード型とドメインモデル型を同一視（持つメソッド・フィールドが違う） |
| export 面（公開 API） | 内部 const を外から呼べると仮定（実は非 export） |
| 関数／メソッドの契約・戻り値 | 戻り値の形・null 可否・例外・バッチ単位を取り違える |
| 外部 API / エンドポイント / 権限 | ホスト・パス・recipient・必要トークン／権限が別物 |
| レスポンス／メッセージ契約 | 既存の出力契約（レスポンス形・スキーマ版）を壊して拡張 |
| 上流ドキュメント | 設計で訂正した事実が要件書に未反映で、下流が古い前提を読む |
| インフラのレール | 同一キュー／worker／状態ストアに別種別を相乗りさせて取りこぼし・汚染 |
| ツール / コマンド / 機能の可否・存在 | 「これは（スキル/CLI/エージェントから）起動できない」「その機能は無い」を未確認で断定（実は起動経路や CLI サブコマンド／設定が在る、または逆に無い） |

この表は「使うべきか」の判定にも使う。**上のどの境界もまたいでいなければ、それは非対象**（同一性が自明な再利用）として軽く扱い、検証手順には入らない。1つでもまたぐなら、その境界について検証手順へ進む。

## 検証手順

1. **境界の種類を特定する。** 上表のどれをまたぐのか。複数なら複数。
2. **一次情報で同一性を確かめる。** 境界の種類ごとに手段を選ぶ。コードの確認は **Serena を既定**とし、型推論やコールグラフが論点のときだけ LSP に上げる（プロジェクトの code-navigation 方針に一致）:
   - 型が同一か／その型がそのメソッド・フィールドを持つか → **既定は Serena** `find_symbol` で型エイリアス・クラス・インターフェースの**定義そのもの**（例: `type X = typeof t.$inferSelect`、クラス本体のメソッド一覧）を読み、持つメンバを事実として確認する。定義文字列だけでは判別できない時（型エイリアス越し・再エクスポート・ジェネリクス・推論後の型）だけ **LSP** `hover`/`goToDefinition` に上げる。LSP は位置指定で落ちることがあるので、落ちたら Serena の symbol body 読みに戻る。
   - シンボルの存在・export 状況・構造・参照元 → **Serena** `find_symbol` / `get_symbols_overview` / `search_for_pattern` / `find_referencing_symbols`。
   - 影響範囲（この再利用面を変えると誰に波及するか）→ コールグラフが要るので **LSP** `findReferences` / `incomingCalls`（使えなければ Serena `find_referencing_symbols`）。
   - ライブラリ・外部 API・公式仕様（エンドポイント／権限／payload 形）→ **Context7**。Context7 が使えなければ公式 docs を WebFetch、それも不可なら「要確認」と明示する。
   - 上流ドキュメント（要件書・設計書）→ 該当ファイルを**実読**して、主張している事実が最新か確認する。
3. **事実・推論・推測をラベルする。** 確認できたものは出典付きで「事実」（file:line／型／refs／docs URL）。確認済み事実から導いたものは「推論」（前提を明示）。裏が取れないものは「推測／要確認」と必ず明記する。
4. **同一でなければ流用しない。** 別実装・アダプタ・分岐に倒す。同一が確認できた境界だけ流用する。「ほぼ同じ」「差し替えるだけ」で押し切らない。
5. **未検証の「同じはず」を下流に流さない。** 検証するまで、それを事実として後続の設計・実装・要件の判断材料に使わない。

## 確認には「否定の確認」も含む

再利用境界を**否定する**こと（「A と B は別物だった」「このメソッドは存在しない」「この型はそのフィールドを持たない」）も、立派な一次情報での確認結果。むしろ再利用の前提を崩す確認は、ほとんどが否定の確認になる。否定が取れたら、それを根拠に流用をやめる判断ができる。

## やってはいけないこと

- **「ほぼ同じだから大丈夫」で流す** — このスキルが潰したい当の失敗。差分が1つでもあるなら境界は別物として扱う。
- **推測を事実として下流に渡す** — 「同形のはず」を確定情報のように設計・要件へ書く。必ず「要確認」を付ける。
- **過剰発火** — 同一性が自明な再利用（同一モジュール内の素直な関数呼び出し等）にまで儀式的に適用しない。判断を要する境界またぎに絞る。
- **検証の名を借りた広範改造** — 確認の範囲を超えて無関係箇所をいじらない。

## 出力（このスキルを使ったと言える状態）

再利用・同一視の判断ごとに、最低限これを残す:

- またいだ境界の種類
- 一次情報での確認結果（手段＋出典）と、事実／推論／推測のラベル
- 同一だったか否か、その結論に基づく流用可否の判断
- 未確認が残るなら「要確認」項目

## 既存ルール／スキルとの関係

- グローバルルール `epistemic-honesty`（事実／推論／推測の区別）と `code-navigation`（Serena 既定・型やコールグラフは LSP）を、「**再利用・同一視を断言する**」という具体トリガーに特化して運用化したもの。
- `extract-testable-module` は「実装した後の責務・凝集の自己評価」。本スキルは「**再利用を断言する前の境界検証**」で、関心が異なる。実装フローでは、断言前に本スキル → 実装後に extract-testable-module、という順で噛み合う。
