# 品質チェックリスト

毎サイクル、以下の4要素を確認する。

## 1. 一貫性（Consistency）

要件間に矛盾がないこと。

- [ ] スコープ（in_scope/out_of_scope）に矛盾がない
- [ ] 制約（technical/business）に矛盾がない
- [ ] 優先度（must_have/wont_have）に矛盾がない
- [ ] 前提条件と制約に矛盾がない

### チェックポイント

```
❌ 矛盾の例:
- in_scope: "リアルタイム通知"
- constraints.technical: "バッチ処理のみ"

✅ 一貫した例:
- in_scope: "リアルタイム通知"
- constraints.technical: "WebSocket使用可能"
```

## 2. 完全性（Completeness）

必要な情報が揃っていること。

- [ ] basic.* の必須フィールドが埋まっている
  - what, why, who は必須
- [ ] must_have に具体的な記述がある
- [ ] 非機能要件の主要項目に記述がある
  - performance, security は推奨
- [ ] 受け入れ基準が定義されている

### 完全性スコア

```
高: 全必須フィールド + 非機能要件 + 受け入れ基準
中: 全必須フィールド + 一部非機能要件
低: 必須フィールドに空きあり
```

## 3. 整合性（Coherence）

論理的に筋が通っていること。

- [ ] why（理由）とwhat（内容）が対応している
- [ ] 制約に違反するmust_haveがない
- [ ] 依存関係が実現可能
- [ ] 既存コードとの整合性がある

### 整合性チェック例

```
❌ 不整合の例:
- why: "コスト削減のため"
- must_have: "最新の有料サービス統合"

✅ 整合した例:
- why: "コスト削減のため"
- must_have: "既存インフラの活用"
```

## 4. 明確性（Clarity）

曖昧さがなく、測定・実装可能であること。

- [ ] 機能要件が具体的で実装可能
- [ ] 受け入れ基準が測定可能
- [ ] 制約に数値や基準が明示されている
- [ ] KPIが定量的に測定可能

### 明確性の判定基準

```
❌ 曖昧な例:
- "高速なレスポンス"
- "使いやすいUI"
- "十分なセキュリティ"

✅ 明確な例:
- "APIレスポンス 200ms以内"
- "3クリック以内で目的達成"
- "OWASP Top 10対応"
```

## 品質サマリーテンプレート

各サイクルで以下の形式で報告:

```markdown

| 要素 | 状態 | 課題 |
|------|------|------|
| 一貫性 | ✅/⚠️/❌ | (あれば記載) |
| 完全性 | ✅/⚠️/❌ | (あれば記載) |
| 整合性 | ✅/⚠️/❌ | (あれば記載) |
| 明確性 | ✅/⚠️/❌ | (あれば記載) |

### 改善が必要な項目
- (課題1)
- (課題2)
```

## 品質ゲート

収束判定の前提条件:

| 要素 | 最低基準 |
|------|----------|
| 一貫性 | ⚠️ 以上（矛盾なし） |
| 完全性 | ⚠️ 以上（必須フィールド埋まり） |
| 整合性 | ⚠️ 以上（論理的整合） |
| 明確性 | ⚠️ 以上（must_haveが明確） |

すべて ⚠️ 以上でないと収束判定に進めない。
