# Bugbot 指摘のトリアージ指針（枝葉でなく根本で見る）

Bugbot の指摘は「絶対の正解」ではない。妥当性・到達可能性・副作用・スコープを
自分で検証してから、対応するか／別チケットへ据え置くかを決める。判断は人間（依頼者）の
承認ゲートを通す。ここはその判断の見取り図。

## 1. 根本原因で束ねる（同じ根の再噴出を見抜く）

Bugbot はラウンドごとに「次のレイヤ」で同種の不整合を再指摘しがち。
複数の指摘が**単一の根本原因**の別レイヤ表出になっていないかを最初に問う。
- 例: 「不正状態（型/データモデルで排除されていない組み合わせ）」を各UIレイヤ
  （エッジ→選択肢→詳細ブロック→ローカルstate→保存データ→カード表示）で
  手作業ガードし続ける、というパターン。
- 束ねられたら、レイヤ個別パッチではなく**根治の置き場所**（型/zod/バリデーション境界、
  ドメイン正規化関数=SSoT、サーバ/エンジン入口ガード）を特定する。

判断に迷う／重い時は `codex`（別プロセスのレビュアー）や `hahifuhe-discuss-review`
（レビュー討議）にクロスチェックを投げる。独立した複数の視点が一致すれば確度が上がる。

## 2. 到達可能性を検証する（これは実際に起きるのか）

「保存JSON/APIは untrusted」は一般原則として正しいが、それは
「この不正状態が実際に発生する」という事実の指摘ではない。
**通常のデータライフサイクルでその状態が生成され得るか**を一次情報（コード）で確かめる:
- 既存/レガシーデータはフォールバックでどう解釈されるか（例: フィールド未指定→既定値）。
- 新規データを作る経路（UI操作・ファクトリ関数）は、その不正な組み合わせを作り得るか。
- どちらも作らないなら、残る発生源は「手細工データ（JSON直編集/API直叩き）」だけ。

到達不能と確認できたら、フロントでの継ぎ足しパッチは過剰になりやすい。
ただし「到達不能だから無対応」で閉じる前に、untrusted 入力境界（保存/エンジン入口）に
**根治バリデーションが存在するか**は必ず確認する（無ければ OQ/別チケットで根治を明記）。

## 3. 副作用ランキング（同じ目的なら侵襲の小さい方）

不整合を解消する手段は、副作用の小さい順に選ぶ:
1. **表示専用の正規化** — 副作用ゼロ。
2. **保存直前の純粋正規化** — 保存アクション時のみ・キャンバス/undo/dirty 非接触。
3. **サーバ/zod で不正状態を弾く** — 境界1箇所で表現。既存 passthrough/後方互換と要調整。
4. **open（読み込み）時の自動データ書換え** — 最も侵襲大。ユーザー操作なしに保存済みデータが
   変わり、dirty 化・undo/snapshot 設計と干渉しやすい。原則避ける。

## 4. 本PR vs 別チケットの線引き

- そのPRのスコープ（例: プロトタイプ＝入口の振り分け検証）を基準に、
  「今ここで閉じるべき表示/整合」と「根治（型/zod/エンジン）＝別チケット」を分ける。
- 別チケットに切るなら、**設計書の Open Question/OQ に根治内容と出典(コミットSHA/指摘)を明記**し、
  Bugbot のスレッドにも事実ベースで返信して握る（到達可能性・根治の置き場所・据え置き理由）。
- 別チケット送りにした指摘は、コード未変更ゆえ次ラウンドで再掲され得る点を許容する
  （返信で「既知・別チケット」と握った前提）。

## 5. 返信の型（各インライン指摘スレッドへ）

- 直した場合: 「修正しました（<commit>）。<何をどう直したか1〜2行>」
- 据え置く場合: 「本PRでは追加対応せず <OQ-x/別チケット> で根治する判断。理由: <到達可能性/根治の置き場所>」
- 採用しなかった代替（例: open時書換え）があれば、却下理由（副作用）も一言添える。
