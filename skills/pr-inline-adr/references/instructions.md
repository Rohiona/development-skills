# PR インラインコメントスキル

PR の差分に実装意図をインラインコメントとして投稿する。
レビュアーが「なぜこう変えたのか」をコードの横で即座に理解できるようにすることが目的。

## コメントの書き方

### インライン ADR（Architectural Decision Record）として書く

各コメントは小さな設計判断の記録。
レビュアーが以下の2点を即座に理解できるように書く:

1. **なぜ変更が必要だったのか** — 変更前の問題・課題・動機
2. **変更によって何が解決されるのか** — 変更後に得られる効果

差分を見ればコードが何に変わったかはわかるので、「何を変えたか」は書かない。

**良い例:**
```
LINEログインの同意画面に友だち追加オプションが表示されない問題があった。
botPrompt を 'normal' にすることで、初回同意時にチェックボックスが表示されるようになる。
```

```
botPrompt の値が2箇所に分散していたため、片方だけ変更される不整合のリスクがあった。
定数化することで、値の変更が1箇所で完結する。
```

**悪い例:**
```
botPrompt を 'none' から 'normal' に変更した。
```
（差分を見ればわかることを繰り返しているだけ。なぜ必要で、何が解決されるかがない）

### パッと見てわからない情報を入れない

チケット番号、Notion の UUID、内部的な参照 ID など、コメント単体で意味が伝わらない情報は含めない。
コメントだけ読んで「なるほど」とわかる内容にする。

**NG:** `（Notion #2073）`、`ref: 276b37cc...`
**OK:** PR 本文の Summary に Notion URL を記載しているので、そちらで十分。

### 句読点で改行する

長い文を1行に詰め込むと読みづらい。
句点（。）や読点の後に改行を入れて、視認性を確保する。

## 投稿手順

### 1. PR の差分情報を取得

```bash
gh api repos/{owner}/{repo}/pulls/{pr_number}/files \
  --jq '.[] | {filename: .filename, sha: .sha, patch: .patch}'
```

ここで得られる `patch` の行番号を使ってコメント位置を特定する。

### 2. コミット SHA を取得

```bash
gh api repos/{owner}/{repo}/pulls/{pr_number}/commits --jq '.[].sha'
```

コミットが複数ある場合、該当ファイルを変更したコミットの SHA を使う。

### 3. コメントを投稿

```bash
gh api repos/{owner}/{repo}/pulls/{pr_number}/comments \
  --method POST \
  -f commit_id="{commit_sha}" \
  -f path="{file_path}" \
  -f body="{コメント本文}" \
  -F line={line_number} \
  -f side=RIGHT
```

`line` は差分の右側（変更後）の行番号。
`-F line=` （大文字 F）で数値として渡す。

### 4. コメントの修正

投稿後に修正が必要な場合:

```bash
# コメント一覧を取得
gh api repos/{owner}/{repo}/pulls/{pr_number}/comments \
  --jq '.[] | "\(.id) \(.path) \(.line) \(.body[:50])"'

# コメントを更新
gh api repos/{owner}/{repo}/pulls/comments/{comment_id} \
  --method PATCH \
  -f body="{修正後の本文}"
```

## コメント対象の選び方

全行にコメントする必要はない。以下の変更にフォーカスする:

- **値の変更**: なぜその値にしたのか（例: `'none'` → `'normal'` の理由）
- **削除**: なぜ消しても安全なのか（例: 重複比較の削除）
- **構造の変更**: なぜこの設計にしたのか（例: 定数化、抽象化）
- **ドキュメントの文言変更**: なぜこの表現にしたのか（例: サービス名を抽象化した理由）

逆に、明らかな追加（新規ファイルの中身すべて等）には不要。

## 行番号のずれ防止

GitHub API の `line` パラメータは差分の右側（変更後ファイル）の行番号。
投稿前に `gh api repos/{owner}/{repo}/pulls/{pr_number}/files` の `patch` を確認し、
実際の差分に表示されている行番号と一致することを検証する。
