# 学習観点（global）— 全領域共通の「責務設計の認識の枠」

`extract-testable-module` が **自己点検時に必ず照合する、領域に依存しない判断の枠**。
人間（閣下）が出した「責務設計のズレ指摘」を `/extract-testable-retro` が蒸留して育てる層。
安定 core（`design-principles.md` の SOLID / 関心の分離 / 揮発↔安定）の**上に乗る学習層**で、core を言い換え・具体化する。

- これは「ケースの山」ではない。**過去傾向を蒸留した有界な"判断の枠"**。点検側はこの集合だけを読む（コンテキスト一定）。
- **上限の目安 12 観点**。超過 or 定期で統合（近接マージ・陳腐化剪定・安定観点の core 昇格を提案＝承認制）。
- **provenance（出典 PR/SHA/セッション/日付/具体ファイル名）はここに書かない**。生ログ `cases.jsonl` にのみ残す。
  ここに具体パス・具体シンボルを書くと「事例メモ」に劣化する（= lens lint で弾く対象）。

## lens ユニット（5枠・責務設計版）

各観点は次の5枠で持つ。**「反例」は必須**（過剰抽出＝浅いモジュール量産への構造的歯止め）。

- **観点**: 何を「責務過多／テスト不能」と見なすか（判断の枠。汎化された言い方で書く）
- **対象**: どんな**コード形状**で起きるか（特定ファイル名でなく「形」で書く）
- **兆候**: 点検時に拾う検出シグナル（モック数・分岐・接続詞・private 数・揮発/安定の跨ぎ 等）
- **処方**: どう割るか（どの関心を・どの単位で・どこへ）。または据え置きの境界
- **反例**: この形なら**据え置きが正**（やりすぎ防止。これを書けない観点は観点になっていない）

## global / 領域別 の判定基準（蒸留時にどちらへ置くか）

- **global に置く**: 判断が**置き場所・命名・テスト配置に依存しない**もの。「副作用の有無で割る」「揮発と安定を跨ぐな」
  「private の数を点検トリガにする」など、どの領域でも同じく成り立つ**判断境界**。
- **領域別に置く**: 「**このプロジェクトのこの領域では**どこへ置くか／どう名付けるか／どこにテストを置くか／何が混ざりやすいか」という
  **その領域固有の具体化・お作法**。
- **矛盾したら global が優先**。領域別は「global 原理のその領域での具体化」に徹し、原理に反する具体化は書かない。
- 迷ったら **まず global の枠で書けないか**を試し、領域固有の置き場所/命名が要るときだけ領域別へ落とす。

## 3段階昇格（過学習の歯止め）

人間の1回の指摘で即 lens 化しない。気まぐれ指摘の過学習を防ぐため次の3段階で扱う:

1. **case**: 初観測。`cases.jsonl` に記録するのみ（観点化しない）。
2. **provisional**: 同種が**2回以上**観測された or **明確な実害**（テストが書けず実バグを通した等）が1回で確認できた → **暫定 lens**として下に追記（見出しに `(provisional)` を付す）。
3. **stable**: provisional が更に再観測され定着 → `(provisional)` を外し**確定 lens**化。十分安定したら core 昇格を提案（承認制）。

各 lens の現在ステージは見出し横の注記で表す（無印＝stable）。ステージ遷移は retro が行い、provenance は cases.jsonl に残す。

### GL1. private／メソッド数そのものを点検トリガにし、1件ずつ裁く

- **観点**: クラスの private（やローカル関数）が増えてきたら、その**数自体を点検の起点**にする。「全体として概ね妥当」という gestalt 判断を禁止し、**各 private を1件ずつ**「薄い I/O 委譲か / 純粋ロジック（分岐・変換・検証・整形・計算）が埋もれているか」で裁く。
- **対象**: private/ヘルパが多いクラス（サービス・クライアント・ハンドラ全般）。
- **兆候**: private が概ね4つ以上、または1つの private 本体に分岐・ループ・変換・検証がある。点検出力（`testability_inventory`）が「各単位」に分解されず1行で「妥当」と言っている。
- **処方**: 純粋ロジックを持つ private は外（module 関数）へ抽出してモック無しでテスト。薄い I/O 委譲だけ内部に残す。点検は必ず単位ごとの表で出す。
- **反例**: 全 private が単一業務タスクのための機能的凝集で、副作用が1つ、引数→戻り値で素直にテストできるなら、**数が多くても据え置き可**（長さ・数は厚さの証拠の1つにすぎない）。

### GL2. 「切り出す」の既定は別モジュール（別ファイル）

- **観点**: 人間が「切り出す」と言ったとき、または純粋ロジックを剥がすとき、既定は**別ファイル（別モジュール）への抽出**。同一ファイル内で関数に割っただけで「切り出した」と見なさない。配置指定が無くても、純粋ロジックは別ファイル module 化を第一候補に検討する。
- **対象**: 厚いメソッド内に埋もれた純粋ロジック。
- **兆候**: 「責務過多を整理した」と言いつつ同一ファイル内の private→private 付け替えで終わっている。人間のイメージ（別モジュール）と出力（同一ファイル分割）が乖離。
- **処方**: 純粋ロジックを別ファイルへ。元は import して呼ぶだけ。元ファイルに定義の残骸を残さない（完全移動）。
- **反例**: 呼び出し元が1箇所のみ・他から使う見込みがゼロ・極小（数行）の純ヘルパは、同一ファイル内関数で足りる（過剰なファイル分割をしない）。

### GL3. 「据え置き」には明示理由＋揮発/安定の非混在チェックを必須にする

- **観点**: 据え置き（切り出さない）を選ぶなら、(a) deletion test で浅い（複雑性を隠蔽していない）こと **かつ** (b) 揮発な adapter と安定な policy が**混ざっていない**ことの**両方**を確認した理由を1行残す。理由なしの据え置きを禁止する。
- **対象**: 「小さいから」「Client だから」「長いだけ」で据え置きたくなる単位。
- **兆候**: 据え置きの理由が書かれていない、または「小さいから」だけ。外部フォーマット変更で純ポリシーのテストが壊れる構造なのに据え置いている。
- **処方**: 据え置くなら理由を `testability_inventory` に明記。揮発/安定が混ざっていたら小さくても割る。
- **反例**: 単一の機能的凝集で副作用1つ、揮発/安定が分かれていない関数は、理由を添えれば据え置きでよい（過剰分割しない）。

### GL4. 下流が未確定なら「揺れる側を吸収する薄いラッパ＋安定な判定」を先に立ててテスト可能化する (provisional)

- **観点**: データの持たせ方・封筒形式など**下流が今後変わりうる**前提があるとき、揺れる側（volatile）を吸収する薄いラッパを用意し、**変わらない判定（routing condition 等の安定 policy）**をラッパ越しにテスト可能な形で分離する。揺れる実装が後で変わっても、安定側のテストは壊れない状態を先に作る。
- **対象**: 仕様が固まりきっていない入口処理・振り分け・設定の取り出し。
- **兆候**: 「この判定ロジックは今後変わるかも」「データをどこに持たせるか一考の余地がある」と分かっているのに、揮発な取り出しと安定な判定が1関数に同居している。
- **処方**: 薄いラッパ（adapter）＋安定判定（policy）＋合成 に分け、判定の真理値表をテスト。実装の揺れはラッパで吸収。
- **反例**: 下流が確定済みで変更見込みがゼロなら、先回りのラッパは過剰（YAGNI）。揺れる根拠が無いのに層を足さない。
