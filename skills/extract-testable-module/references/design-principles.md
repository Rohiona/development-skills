# 設計原則の使い方（責務 × コードベース × 要件/文脈）

このスキルが「適切な凝集度」を判断するための見取り図。原則は教条ではなく道具として使う。
上位目的は常に **テスト容易性・責務の明快さ・最小侵襲**。原則を満たすこと自体を目的化して過剰分割してはいけない。

## 1. 単一責任（SRP）— 責務とは「変更理由」

SRP の「責任」は機能の粒度ではなく **変更の理由**。1 つのモジュールは 1 つの変更理由だけを持つべき、という指針。
「このコードはどんな理由で変更されるか」を列挙し、理由が複数あれば責務が複数ある。

見分け方:

- 説明に「そして」「それから」が複数回出る → 複数責務の疑い
- 「料金計算の仕様変更」と「保存先 DB の変更」が同じ関数を触らせる → 別の変更理由が同居している
- 変更理由が違うものは、別々のタイミングで別々の人が変える。だから別々に置くと、変更もテストも局所化する

例: `createWorkflow` が「リクエストの検証ルール」「DB スキーマへの変換」「永続化」を持つなら、
検証ルールの変更・変換の変更・永続化の変更は別々の理由。検証＋変換（純粋）を関数に切り出せば、
仕様変更のテストは純粋関数だけで閉じる。

## 2. 関心の分離 — 境界をどこに引くか

「関心（concern）」は「気にすべき事柄の種類」。種類の違うものを混ぜないことで、各々を独立に理解・変更・テストできる。
このスキルで実利的な境界は次の 3 つ。

### (a) 純粋ロジック ↔ 副作用（最重要）

入力→出力が決定的な計算・判断・変換（純粋）と、DB / HTTP / queue / 時刻 / 乱数（副作用）を分ける。
純粋側はモック無しで全分岐をテストでき、副作用側は薄い配線に収まる。**厚いメソッド分解の主戦場**。

### (b) 業務的関心 ↔ 技術的関心

「クーポンは月内 1 回まで」は業務的関心。「JSON をパースする」「SQS に送る」は技術的関心。
業務ルールを技術詳細から引き剥がすと、業務ルールが読める・テストできるコードとして独立する。
業務の関心の単位で小さく分け、データとそれを使う判断ロジックを同じ場所に集めると、凝集が上がりテストが書きやすい。

### (c) 方針（ポリシー） ↔ 手順（メカニズム）

「何を達成するか（高レベルの調整）」と「どうやるか（低レベルの実装）」を分ける。
高レベルの調整は元のメソッドに薄く残し、低レベルの手順を切り出すと、抽象度が揃って読みやすくなる。

### (d) 揮発 ↔ 安定（変更頻度 = rate-of-change）

「どれくらいの頻度で・どんな外圧で変わるか」が違うものを混ぜない。これは (a)〜(c) と直交する、もう 1 本の境界線。

- **揮発（volatile）** — 外部フォーマット・外部契約・インフラの都合に結びつき、それが変わると追従して書き換わる部分。例: 「メッセージ封筒のどのフィールドに platform 情報が載っているか」「protobuf のどのキーか」「SQS のどの属性か」。**adapter（翻訳・取り出し）**の関心。
- **安定（stable）** — 業務の純ポリシー・判定で、外部フォーマットが変わっても変わらない部分。例: 「platform kind → どのルートへ流すか」「料金 → 割引区分」。**policy（決定）**の関心。

**1 つの関数が揮発な取り出しと安定な判定をまたいでいたら、たとえ小さくても層として割る。** 揮発側（adapter）が変わっても安定側（policy）のテストは 1 行も直さなくて済み、逆も同じ。変更理由（SRP）が「外部フォーマットの変更」と「業務ルールの変更」で別だからで、SRP を rate-of-change の語彙で言い直したものと考えてよい。

> 例: 配信先の振り分け。`extractPlatformKind`（封筒のどこに platform が載るか = 揮発な adapter）と `routeForPlatformKind`（kind → route の純ポリシー = 安定）を 1 関数に混ぜると、封筒形式が変わるたびにルーティングのテストまで巻き添えで壊れる。2 つに割り、合成 `resolvePlatformRoute` で繋ぐ。before→after は `extraction-patterns.md` を参照。

**deletion test との優先関係**: deletion test は「浅い（pass-through）なら切らない」と教えるが、揮発/安定の境界をまたぐ小関数は deletion test 上は浅く見えても**分離を優先してよい**。剥がすのは「複雑性の隠蔽」のためだけでなく、「変更の波及を断つ」ためでもある。両者がぶつかったら、揮発/安定が本当に混ざっているか（=外部フォーマット変更で純ポリシーのテストが壊れるか）で決める。混ざっていないなら deletion test に従い据え置く。

### (e) 型で関心を表現する（型安全な設計）

関心の分離は関数の分け方だけでなく **型の設計** にも現れる。層を割っても、層の境界（接合面）を型が支えていないと
「割ったのに取り違えは防げない」状態になる。実利的な指針は 3 つ:

- **プリミティブの引き回しで関心を溶かさない** — `(userId: string, planCode: string, tier: string)` のような同型引数の並びは、
  取り違えてもコンパイラが検出できない。まず引数の数を減らす分離を考え、それでも残るなら意味のある型
  （union・オブジェクト・既存のドメイン型）で区別する。ただし branded type 等の**新基盤の持ち込みは YAGNI** —
  コードベースに既にある流儀（zod スキーマ・生成型・union 型）に合わせる。
- **不正な状態を型で作れなくする** — 「どちらか一方だけ入る optional 2 つ」より判別可能 union（discriminated union）。
  分岐が union の全ケースを網羅しているかは `switch` の網羅性チェック（`default` で `never` に代入）でコンパイラに監視させる。
  仕様追加（ケース追加）のとき、直すべき場所を型エラーが列挙してくれる状態が理想。
- **parse, don't validate（検証したら検証済みの型で返す）** — 外部から来た値の検証（adapter 層）は boolean を返して
  終わりにせず、**絞った型を返す**。裸の `as` キャストは「検証せずに型を宣言した」だけで、せっかく分離した adapter 境界を
  型の上では放棄している。type guard（`v is T`）・`z.parse`・検証付きファクトリ等、コードベースの流儀で絞る。
  （機械検出: `verify-extraction.py` の W3 が裸の `as` を WARN する。）

これは (a)〜(d) で割った層の**接合面を固くする**話であり、割り方そのものは (a)〜(d) で決める。
型のためだけの抽象（使わない generics・過剰な branded type）は過剰抽象で、凝集度の節（§4）の断片化と同罪。

## 3. 依存性逆転（DIP）— テスト可能性の鍵

具体的な外部依存（実 DB クライアント、実 API クライアント）を関数内で直接 `new`・直接呼び出しすると、テストで差し替えられない。
**抽象（インターフェース）に依存し、依存は外から注入する**。注入の形（コンストラクタ／引数／DI コンテナ）はコードベースの流儀に合わせる。

DIP が効くのは「外部依存に触る責務」を切り出すとき。純粋ロジックには依存が無いので DIP は不要。
まず純粋ロジックを剥がし、残った副作用部分にだけ DIP を適用するのが順番として効率的。

## 4. 凝集度 — 良い集まり・悪い集まり

凝集度は「1 つのモジュール内の要素がどれだけ密接に関連しているか」。高いほど良い。

- **機能的凝集（理想）** — すべての要素が単一の明確なタスクに寄与する。切り出しのゴール。
- **論理的凝集・偶発的凝集（避ける）** — 「なんとなく関連」「たまたま同じ場所」で集めたもの。`utils` への雑多な寄せ集めはこれに陥りやすい。

**過小分割は凝集度を下げる**。常に一緒に変わるもの、単独では意味をなさないものを無理に分けると、
変更のたびに複数ファイルを触る羽目になり、かえって悪化する。「関連するものは一緒に、無関係なものは分けて」。
1 行関数の量産は分割ではなく断片化。

## 5. 3 要素の掛け合わせ（実例）

責務・コードベース・要件/文脈は、別々に見ると判断を誤る。掛け合わせて初めて「適切な凝集度」が決まる。

**例: ワークフロー作成リクエストの処理が厚い**

- **責務**: ①入力の検証 ②protobuf→DB 入力への変換 ③永続化。①②は純粋、③は副作用。→ ①②を剥がす候補。
- **コードベース**: このリポジトリは純粋関数を `{domain}/utils/` に置き、co-location でテストする慣習。→ `workflow/utils/build-workflow-input.ts` に置き、隣に `.test.ts`。
- **要件/文脈**: 今回の要件は「作成 API の追加」。検証ルールは今後増える見込み。→ 検証を独立関数にすれば将来のルール追加が純粋関数テストで閉じる。汎用バリデーション基盤の新設は要件に無いのでやらない。

結論: ①②を `build-workflow-input.ts` に Extract、③はサービスに残す。検証分岐を純粋関数でテスト。侵襲は新規 1 ファイル＋サービス内の数行置換に収まる。

**分割しない判断もある**: 「厚い」関数が単一の業務タスクのための機能的凝集で、副作用も 1 つ、テストも素直に書けるなら、行数が多くても切り出さない。長さは厚さの証拠の 1 つにすぎず、長さそのものが罪ではない。

## 6. 原則を道具として使う（やりすぎないために）

- 原則は「一貫した判断のための共通言語」であって、満たすこと自体がゴールではない。上位目的はテスト容易性・責務の明快さ・最小侵襲。
- 「SOLID 的に正しいから」を理由に、要件に無い抽象化・汎用化・インターフェース増殖をしない（YAGNI）。
- 迷ったら問い直す: 「この分割で、テストは書きやすくなるか？ 触るファイルは増えすぎないか？ 既存の慣習に沿うか？」 3 つとも Yes なら分割、どれかが No なら立ち止まる。
