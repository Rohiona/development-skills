# area-map — パス → 領域キー ルーティング

自己点検（`testability_inventory`）と `/extract-testable-retro` の両方が、**編集した実ファイルのパス**から
「どの領域(area)か」を判定するための対応表。点検時はここで領域を引き、**`learned-lenses.global.md`（全領域共通）
＋ 該当領域の `learned-lenses/<area>.md` の1枚だけ**を読む（コンテキストを軽く保つ）。

## 使い方（点検側）

1. いま編集した実ファイルの repo 相対パスを取る（複数なら各々）。
2. 下表を**上から順に**マッチさせ、最初に当たった `area` を採用（上ほど具体的＝優先）。
3. どれにも当たらなければ `area = (none)`。global lens のみ照合する。
4. `learned-lenses.global.md` ＋ `learned-lenses/<area>.md`（存在すれば）を Read して照合する。

## 使い方（retro 側）

蒸留する Missed のケースの `path` から同じ表で `area` を決め、その領域の lens ファイルへ蒸留する
（global に置くか領域別に置くかの最終判断は `learned-lenses.global.md` 冒頭の「global/領域別の判定基準」に従う）。
新しい領域が必要になったら、この表に行を1つ足し、`learned-lenses/<area>.md` を新設する。

## 粒度の方針（F: 領域粒度誤りの歯止め）

**最初は粗く**（apps / packages / cdk 単位）。細分化するのは「同じ粗い領域の中で、置き場所・命名・テスト慣習が
**実際に**割れた指摘が出たとき」だけ。投機的に細かい領域を先に作らない。lens ファイルは**実際に蒸留する種が
できた領域だけ**作る（空ファイルを先に量産しない）。

## 対応表（上ほど優先）

> **以下の 3 行は記入例（プレースホルダー）です。** 導入先プロジェクトで、自分のリポジトリ構造に
> 合わせて行を書き換え・追記してください（粒度は下の「粒度の方針」に従い、最初は粗く）。

| # | パターン（glob/部分一致） | area キー | 領域の性格 |
|---|---|---|---|
| 1 | `packages/<共有pkg>/**/client/**`, `**/*Client.ts` | `api-clients` | （記入例）外部 API / SDK ラッパ。request 組立・response 解析・error 写像・ページングが private に埋もれやすい |
| 2 | `apps/<APIサーバー>/**` | `api-server` | （記入例）ルーティング・スキーマ・サービス層。宣言と派生/変換ロジックが混ざりやすい |
| 3 | `apps/<フロントエンド>/**` | `frontend` | （記入例）UI。表示整形・導出（純粋, `*/utils/`）とコンポーネント/フック |

> `extraction-out`（＝抽出して出来た純粋ロジック・util モジュール側）は領域ではなく **抽出の出力先**。
> 「抽出先にまた詰め込む」再発防止の観点は global lens 側で扱う（領域キーにしない）。

## 注意

- 廃止予定のディレクトリ（deprecated なアプリ等）には新規 lens を生やさない（凍結保守のみ）。指摘が出ても cases.jsonl 記録に留め、観点化しない。
- 1ファイルが複数領域にまたがる稀なケースは、**主たる責務の置き場所**で1つに決める（点検は global + 1領域が原則。2枚読みは例外）。
