# extract-testable-module

実装したコードの責務設計を能動的に自己評価し、テストできる凝集へ切り出すスキル。

## このスキルの本質

AI エージェントは「1 つのモジュールに収めたい」という引力に従いやすく、放っておくと private メソッドや
ローカル関数に処理を厚く詰め込む。入力検証・変換・分岐判断・永続化・外部 API 呼び出しが 1 メソッドに混ざると、
単体テストに大量のモックが要り、分岐の組合せでテストが爆発し、結局テストが書かれない。

**根本原因（"private が多い"の正体）**: この詰め込みは、AI が「**既存の構造を崩したくない**」というミニマム方針に流れ、
本来**責務の違うコードを同じモジュールに private メソッドとして同居**させることで起きる。設計書や要件に実装ルールが
書かれていないと、AI は「最小改変」を安全策として選び、責務違いを private 化で吸収してしまう。だが正しいのは、
**既存コードベースは尊重しつつも、責務が違うものは private 化で同居させず、単体テスト可能・高凝集の独立単位にして
「仕様が将来膨れても単体で対応できる」状態を作る**こと。責務が違うなら **Sprout（既存にほぼ触れず独立モジュールを新設）**で
出せば、挙動不変・最小侵襲・テスト可能の 3 軸を同時に満たせる。「最小改変だから private に足す」より「責務が違うなら
別単位＋テスト」を優先する——これがこのスキルの設立思想であり、点検の起点。（最小改変が常に悪なのではない。
"責務違いの同居" だけが問題で、同じ責務の機能的凝集に収まるものは無理に外出ししない。）

だからこのスキルの主役は **受動的な切り出し依頼ではなく、能動的な自己評価** にある。
実装を一区切りつけたら、指示を待たずに手を止め、「いま書いたコードの責務設計は、要件・文脈・コードベースに照らして
適切か」を自分で問い直す。問い直して必要があれば、自分の判断で切り出す。指示されて初めて動くのでは、
このスキルの意味がない。

## いつ発火するか（能動が主）

- **機能を実装し終えた直後** — コミット前・報告前に、自分の実装を一度評価するターンとして
- **実装系スキル／フローの仕上げ** — 実装が走った後の品質ゲートとして
- **厚いメソッドを書いている自覚が出た瞬間** — 1 関数が育ってきた、モックが増えそうだと感じたとき
- **明示的な依頼**（受動の呼び出し口）— 「切り出して」「テスト可能にして」「責務過多を直して」など

## 絶対に外さない 3 つの軸（衝突時の優先順）

1. **挙動を変えない** — 切り出しは等価変換。観測可能な振る舞いを 1 ミリも変えない。型・ビルド・テストで担保する。既存テストが無い場合は、抽出を「ロジックを 1 行も変えない純粋な移設」に徹し、抽出先に書いた新規テストで挙動を固定する。それが等価性の担保になる。
2. **侵襲を最小化する** — 既存への変更と、1 つの開発で触るモジュール数を最小に。関係ない箇所は触らない。リファクタリングは目的ではない。
3. **テスト可能な凝集をつくる** — 切り出した単位は関連するものだけが集まり、外部依存から切り離され、入出力で検証できる。そして実際にテストを書いて green にする。

「3 のために 2 を破る」（テストのために広範改造する）は本末転倒。迷ったら侵襲の小さい方を選ぶ。

## 中核：実装後の自己評価ゲート

実装したら、切り出しに入る前に、まずこのゲートを通す。**コードを評価するのであって、書き直すと決めつけない。**
問題が無ければ「責務設計は妥当」と判断して通過してよい。過剰な分割は 3 軸に反する。
ゼロから新規実装する局面でも同じで、書く前・書きながらこの問いを前倒しで適用してよい（ゲートは「実装後」に限らない。要は放置せず責務を能動的に設計すること）。

自問する順番:

1. **要件・文脈は何だったか** — このコードは何のために存在するのか。達成したい業務上のゴールは何か。これを思い出さないと「責務」を正しく切れない。
2. **責務はいくつあるか** — このメソッド/関数が担っている「変更理由」を数える。「〜して、それから〜して」と接続詞で説明が伸びるなら複数責務。**単一責任（SRP）** の観点。
3. **関心が混ざっていないか** — 業務的判断と技術的詳細、純粋なロジックと副作用（I/O・時刻・乱数）が同じ場所に同居していないか。**関心の分離** の観点。あわせて **rate-of-change（揮発↔安定）** も見る: 1 つの関数が「外部フォーマット・契約に結びつく揮発な取り出し（adapter）」と「外部が変わっても変わらない安定な判定（policy）」をまたいでいたら、たとえ小さくても層が混ざっている疑い。
4. **コードベースに照らして配置・分割は妥当か** — 既存の層・慣習なら、この責務はどこに置かれるはずか。今の置き方はそこから外れていないか。
5. **テストを書けるか** — いま単体テストを書くとして、何をモックする必要があるか。多いなら、純粋ロジックと依存が絡まっている証拠。
6. **型は関心を表現しているか** — 生の string/number の引き回しで取り違えが起きる引数並びは無いか。不正な組合せが型レベルで作れてしまう構造（optional だらけの入れ物等）は無いか。検証したら検証済みの型で返しているか（parse, don't validate — 裸の `as` キャストで境界を越えない）。**型安全な関心の分離** の観点（詳細は `references/design-principles.md` の 2-(e)）。

このゲートの結論は「分割する／しない」の二択ではなく、「**どの関心を、どの単位で、どこへ**切り出すと、最小侵襲でテスト可能になるか」を見定めること。

### 学習観点を必ず照合する（area-map → global + 領域別 lens）

自問する前に、**いま編集した実ファイルのパス**から領域を引き、過去に人間（閣下）の指摘から蒸留された学習観点を必ず照合する。これをしないと、同じ指摘を何度も人間に言わせることになる。

1. `references/learned-lenses.global.md`（全領域共通の判断の枠）は **領域に関わらず毎回必ず読む**。これは累積した自己学習の土台で、コスト承知で常時照合する。
2. `references/area-map.md` で、編集したファイルのパス → 領域キー(area) を判定し、`references/learned-lenses/<area>.md`（その領域のお作法。存在すれば）を読む。領域別はその領域の分だけ読む（無関係領域のお作法を読んでも学習にならず雑音になるため、領域別だけは該当分に絞る）。
3. 各観点の「兆候」を今の実コードに当てて、当たっていれば「処方」に従う。「反例」に該当するなら据え置く。

### 自己点検は構造化出力で残す（testability_inventory）

点検した「フリ」（compliance theater）を防ぐため、結論は散文で「妥当」と言わず、**単位ごとの棚卸し表**として出す。クラス/モジュールの **private・ローカル関数・厚いブロックを1件ずつ**裁き、gestalt な「概ね妥当」を禁止する。

**網羅性も自己申告にしない。** 表を書く前に、対象ファイルの単位を機械で列挙し、列挙された全単位が表に載っていることを突合する（載っていない単位が 1 つでもあれば網羅性不足＝ゲート未通過。public メソッド・厚いブロックは列挙対象外なので手動で表へ追加する）:

```bash
python3 ~/.claude/skills/extract-testable-module/scripts/verify-extraction.py --list-units --file <編集した実ファイル> [--file ...]
```

```
### 責務自己点検（testability_inventory）
対象: <file:symbol> ／ 領域: <area-key>（area-map 判定）／ 照合 lens: global + <area>
| 単位（private/関数/ブロック） | 関心 | 純粋ロジック | モック要否 | 判定 | 理由・処方（据え置きは理由必須） |
|---|---|---|---|---|---|
| parseRecurringExecution | 変換 | 有 | 不要 | 抽出 → workflow-input.ts | 純粋・分岐あり。GL1/AC1 該当 |
| sendRequest | I/O 委譲 | 無 | （HTTP） | 据え置き | 薄い委譲。揮発adapter/安定policy 非混在を確認(GL3) |
結論: 抽出 N 件 / 据え置き M 件（各理由付き）。照合した lens: …
```

- **据え置き行には必ず理由**（GL3）。「小さいから」だけは不可。揮発/安定が混ざっていないことの確認を1語添える。
- 設定/ドキュメントのみ等で点検不要と確信できるターンは、表の代わりに「責務自己点検 不要（理由）」の1行でよい。
- この表を出すこと自体がゲート通過の証跡。**表を出さずに「責務設計は妥当」と述べない。**

## 判断フレーム：責務 × コードベース × 要件/文脈

「適切な凝集度」は抽象論では決まらない。次の 3 つの掛け合わせで具体的に決める。

- **責務（何を）** — SRP と関心の分離で、切り出すべき関心の単位を見極める。純粋ロジック／外部依存／オーケストレーションを区別する。
- **コードベース（どこへ・どんな形で）** — 既存の層・命名・テスト配置・依存注入の流儀に倣う。新しい流儀を持ち込まない。隣の人が選ぶ置き場所に合わせる。
- **要件/文脈（なぜ・どこまで）** — その実装が果たす業務上の意味と、変更の射程。要件に無い汎用化・抽象化はしない。今のゴールに必要な分割だけを行う。

原則（SRP・関心の分離・DIP・凝集度）は教条ではなく、この 3 要素を一貫して判断するための **見取り図** として使う。
原則の使い方の詳細は `references/design-principles.md` を読む。

## 切り出す価値があるか：deletion test（削除テスト）

切り出す前に「そのモジュールは複雑性を肩代わりしているか」を deletion test で確かめる。過剰抽出（浅いモジュールの量産）を防ぐための歯止め。

- **問い**: もしこのモジュール（切り出し候補）を削除して呼び出し側にインライン展開したら、複雑性はどうなるか。
  - **N 箇所の呼び出し側に複雑性が分散・再出現する** → そのモジュールは複雑性を隠蔽できている＝**深い（deep）**。切り出す価値あり。
  - **複雑性がほぼ消える（ただの薄い受け渡し）** → **pass-through（浅い）**。切り出してもインターフェースという名の負債が増えるだけ。切り出さない。
- **テストのためだけに 1 行の純粋関数を剥がす**のは典型的な浅いモジュール。これ自体は禁止しないが、deletion test を通らないなら「呼び出し側に残してそのまま検証できないか」を先に検討する。
- 深いモジュール = 単純なインターフェースの裏に実質的な複雑性（不変条件・エラー処理・順序・分岐）を畳み込めているもの。切り出しは「テスト可能化」と同時に**この深さを得られるか**で判断する。

deletion test に通る切り出しを優先し、通らないものは Sprout/Extract 以前に「切り出さない」を選ぶ。

**例外：rate-of-change（揮発↔安定）が deletion test に優先する場合がある。** deletion test 上は浅く見えても、1 つの関数が「揮発な adapter（外部フォーマット・契約の取り出し）」と「安定な policy（純粋な判定）」をまたいでいるなら、層として分離してよい。剥がす目的は複雑性の隠蔽だけでなく **変更の波及を断つ** ことにもあるからで、揮発側が変わっても安定側のテストが 1 行も壊れない状態を作れる。両者がぶつかったら「外部フォーマットの変更で純ポリシーのテストが壊れるか」で判断する（壊れるなら混ざっている＝割る、壊れないなら deletion test に従い据え置く）。詳細と before→after は `references/design-principles.md` の (d) と `references/extraction-patterns.md` の §6。

「据え置き（切り出さない）」を選ぶのは、過剰抽出の歯止め（deletion test）に加えて **揮発と安定が混ざっていないことを確認した上で** のみとする。長い・厚いだけで揮発/安定が分かれていない機能的凝集なら据え置きでよいが、「小さいから・浅いから」だけを理由に揮発/安定の混在を見逃して据え置くと、今回の取りこぼし（層分離をスキルでなく対話から出した）を繰り返す。

## 何を切り出すか（純粋ロジック最優先）

テスト容易性あたりのコストが最も低いものから剥がす。優先順:

1. **純粋ロジック** — 入力から出力が決定的で副作用がない部分（パース・バリデーション・変換・計算・判定）。引数と戻り値だけでテストでき、モックが要らない。**最大の収穫**。厚いメソッドの大半はここを剥がすだけで激変する。
2. **外部依存に触る責務** — DB・API・queue など。依存を注入可能にして（DIP）切り出す。
3. **オーケストレーション** — 上記を順に呼ぶ「調整役」。呼び出し側に薄く残すのが自然で、無理に切り出さない。

純粋ロジックと I/O を **一緒に** 切り出してはいけない。混ぜると切り出し先でも結局モックが要る。境界は「副作用の有無」で引く。これが関心の分離の最も実利的な使い方。

## どこへ置くか（既存アーキテクチャに倣う）

実行時に必ず近隣を調査してから決める（手順は `references/workflow.md`）。同種の責務の置き場所、命名規則、
テストの配置とフレームワーク、依存注入の流儀を事実で確認し、それに合わせる。過小分割（1 行関数の乱立）も
過剰抽象（使う当てのない汎用化）も避ける。切り出した単位に名前を付けて「と」が要る（`parseAndValidateAndSave`）なら、まだ多責務。

## Sprout か Extract か（侵襲で決める）

| 技法 | 何をするか | いつ選ぶか |
|---|---|---|
| **Extract（抽出）** | 既存メソッドの一部を関数/モジュールに切り出し、既存はそれを呼ぶだけにする | 既存を安全に分解できる。純粋ロジックを剥がす王道 |
| **Sprout（芽吹き）** | 新しい責務を別モジュールとして新設し、既存からは最小限の 1 呼び出しだけ足す | 既存が巨大・複雑で分解リスクが高い／新規ロジックの追加。**既存にはほぼ触らない** |

判断は侵襲の大きさ。既存への変更が小さく等価性を保てるなら Extract、既存に手を入れると変更が膨張する・安全な分解の確証が持てないなら Sprout。
既存の private を別の場所からも使いたくなったら、そのロジックを独立モジュールへ Extract して共有する（コピペしない）。
**触るモジュール数を増やさない** ことを優先し、Extract で既存を広く触ることになるなら Sprout に倒す。

### 切り出し先を先に確定する（同一ファイル内の関数 か 別ファイルのモジュール か）

着手前に、切り出し先が **同一ファイル内の関数分割** なのか **別ファイル（別モジュール）への新設/移設** なのかを必ず確定する。ここを曖昧にしたまま手を動かすと、別ファイル新設が要件なのに同一ファイル内で関数に割っただけ、という取り違えが起きる。

- 依頼に「別モジュールに」「別ファイルに」「モジュールとして切り出す」とあれば、同一ファイル内の関数分割で済ませてはいけない。新しいファイルを作って配置する。
- 依頼が「責務過多を整理して」程度で配置の指定が無いときは、**責務 × コードベース × 要件/文脈** と侵襲最小で別ファイルか同一ファイル内かを決める。判断がつかなければ着手前に確認する。

### 移動は完全に行う（元ファイルに残骸を残さない）

別ファイルへ移すと決めたら、定義を **元ファイルから削除して移動** する。元に定義を残したまま新ファイルにも置く（二重定義）、あるいは元ファイルに古い定義が残る、は不完全な移動でレビューの往復を生む。

- ts-morph / Serena でシンボルを移動し参照を更新したあと、**元ファイルに移動対象の定義が残っていないこと** を検索で検証する。
- 元の呼び出し側は、新モジュールを import して呼ぶだけの形に変わっていることを確認する。

## 施術して、テストして、報告する

詳細手順は `references/workflow.md`、技法の before→after は `references/extraction-patterns.md`。要点:

- Serena でシンボル移動・参照更新、LSP で型・コールグラフ確認、`ts-morph` MCP で機械的な移動（手作業の取りこぼし防止）
- 切り出した単位に単体テストを書く。**プロジェクトのテストフレームワークと配置慣習に従う**
- 型チェックとテストを実行し green を確認する。落ちたら直す。確認せず「できました」と言わない
- 報告に「触ったファイル一覧」「切り出した単位・置き場所・選んだ技法と理由」「テスト結果」「等価性の根拠」を含め、侵襲が最小に収まったことを示す

## 中核：抽出後の自己検証ゲート（extraction_verify）

事前の自己評価ゲート（`testability_inventory`）が「**どう割るかの意思決定**」なら、こちらは「**割った結果が本当にテスト可能な構成になったか**」を、切り出しとテスト作成の後に **AI の自己申告でなく機械で答え合わせ**する事後ゲート。「テスト可能にした」と散文で言い切る前に、**単位ごとの PASS/WARN/FAIL 表**を出す。これが最大の失敗モード（compliance theater＝点検したフリ）への歯止め。

手順・チェック項目の全定義は `references/workflow.md` の §7a、機械照合は `scripts/verify-extraction.py`。要点だけ:

- **構造 FAIL が 1 つでもあれば、型/テストが緑でも「完了」と言わず手順に戻す。** 「緑だが構造が外れている」を捕まえるのが事後ゲートの存在意義。FAIL の柱＝**完全移動／直接 import 配線／純粋なのにモックが要らないこと／export-as-private でないこと／等価性(tsc・test green)／無意味テストでないこと／（条件付き）micro-mutation でテストが赤化すること**。
- **判定不能はPASSにしない**（UNVERIFIED＝要手動確認として残す）。黙って通すのも、一律で止めるのもしない。
- **自己成長（self-oracle）**: 機械確定シグナル由来の FAIL が事前ゲートの見落としだったら、`cases.jsonl` に self-missed case を記録して反省材料にする。ただし **`stage:"case"` 固定・自動昇格なし・dedupe あり**（自己参照汚染の防止）。ルール(lens)への格上げは `/extract-testable-retro` で**人間の承認を経てのみ**。主観判断は self-case にせず、従来どおり人間オラクルに委ねる。

## やってはいけないこと

- **厚いメソッドを丸ごと別ファイルへ移すだけ** — 場所が変わっただけで責務は分かれていない
- **配置の取り違え／不完全な移動** — 「別モジュールに」と言われたのに同一ファイル内で関数に割っただけ、または別ファイルへ移したつもりで定義を元ファイルに残す（二重定義・残骸）
- **純粋ロジックと I/O を一緒に切り出す** — 切り出し先でも結局モックが要る。境界は副作用の有無
- **export-as-private（テストのために内部を晒すだけ）** — 混在した関数の内部分岐をそのまま `export` する／private を public にするだけで「テスト可能にした」と呼ばない。責務は割れておらず、揮発/安定も混ざったまま、テストの依存も減らない。正は責務の再概念化＝層分離（adapter / policy / 合成）。対比は `references/extraction-patterns.md` の §6
- **広範リファクタへの暴走** — 依頼/評価対象の外（命名統一・フォーマット・無関係ファイル）に手を出さない
- **挙動の変更** — 「ついで」のバグ修正や仕様変更を混ぜない。気づいた問題は別途報告する
- **新モジュールへの再・詰め込み** — 切り出した先にまた何でも入れたら同じ問題の移動
- **テストの未実行** — 書いたら必ず走らせて green を確認する
- **原則のための分割** — SOLID を満たすこと自体を目的化して過剰分割しない。上位目的はテスト容易性と責務の明快さ

## 対象外（このスキルを使わない場面）

型エラー/ビルドエラーの修正・命名やフォーマットの整理・性能改善・既存構造のままのテストカバレッジ追加が主目的の依頼には使わない（それぞれ別の手段に譲る）。
