# Git Sweep — ブランチ・ワークツリーの安全な条件付き掃除

## 原則（なぜこの手順か）

ブランチ・ワークツリーの削除は、未マージのコミットや未コミットの作業を巻き込むと不可逆の損失になる。だからこのスキルは fail-closed で動く:

- **「消してよい証拠」が一次情報で取れたものだけ**削除候補に載せる。証拠が取れないものは残す（残す側に倒す）
- **git が安全弁を持つコマンドだけを自分で実行する**。`git branch -d`（未マージなら拒否される）と `git worktree remove`（未コミット差分があれば拒否される）の2つ。安全弁を外すコマンド（`branch -D`、`worktree remove --force`、`push --delete` 等）は**どんな根拠があっても自分で実行せず**、証拠を添えてユーザーに手動実行を委ねる。プロジェクトにこれらをブロックするフックがある場合、それは正常動作であり迂回しない
- 実行前に必ず**棚卸し → 分類表 → 範囲の承認**を挟む。承認なしで消し始めない

## Step 1: 棚卸し（読み取りのみ）

まずデフォルトブランチを特定する（`develop` と決めつけない）:

```bash
git symbolic-ref refs/remotes/origin/HEAD --short 2>/dev/null || echo "origin/HEAD 未設定 — ユーザーに確認"
```

続けて現状を取る:

```bash
git worktree list
git branch -vv                      # gone 検出（": gone]" を含む行）
git branch --merged <default>      # マージ済み判定（※squash マージは検出できない）
```

ワークツリーごとに未コミット差分の有無も見る: `git -C <worktree-path> status --porcelain`

## Step 2: 4区分に分類して表で提示

棚卸し結果を次の4区分に仕分け、**表にしてユーザーに見せる**（区分・対象・安全性の根拠を列にする）:

| 区分 | 条件 | 処理 |
|---|---|---|
| A: マージ済みブランチ | `--merged` に載っている ∧ 現在ブランチでない ∧ どのワークツリーにもチェックアウトされていない | `git branch -d` |
| B: 残骸ワークツリー | リポジトリ内（`.claude/worktrees/` 等）∧ 未コミット差分なし ∧ HEAD のコミットがデフォルトブランチに含まれる（`git merge-base --is-ancestor` で確認） | `git worktree remove` → 付随ブランチが A 条件なら `-d` |
| C: gone ブランチ | 追跡先リモートが消えている（squash マージ済みの可能性大だが未確認） | Step 3 の裏取りへ |
| D: 触らない | 上記の証拠が揃わないもの全部: 未マージ・進行中の外部ワークツリー・`backup/` 等の退避ブランチ・未コミット差分あり | 対象外と明記して残す |

プロジェクトにレビュー用ワークツリーの掃除スクリプト（echo なら `~/.claude/scripts/review-worktree-clean.sh`）があり `review/` 目印の資産が残っていれば、その分は独立区分としてスクリプトに任せる（自前で消さない — スクリプト側がスコープを保証しているため）。

## Step 3: gone ブランチの裏取り（squash マージ対策）

`--merged` の機械判定は **squash マージを見逃す**（履歴上は別コミットになるため）。gone ブランチは「リモートが消えた」だけでマージ済みの証明ではないので、GitHub で実測する:

```bash
gh pr list --head <branch> --state all --json number,state,mergedAt --limit 5
```

- **MERGED の PR が見つかった** → 内容は取り込み済み。ただし squash マージだと `git branch -d` は通らないため、削除は `-D` になる。**`-D` は実行せず**、PR 番号・マージ日時を根拠として添えてコマンドをユーザーに提示する
- **見つからない／CLOSED のみ** → 放棄されたのか未マージなのか判断できない。区分 D（触らない）に落とし、その旨を報告する

## Step 4: 範囲の承認を取ってから実行

AskUserQuestion（複数選択可）で「どの区分まで消すか」を確認する。質問文と選択肢に「選ぶと何が消えるか・なぜ安全か」を日常語で書く（選択 UI では直前の本文説明は読まれない前提で書く）。

承認された区分だけ、この順で実行する:

1. レビュー用スクリプトがあれば実行（区分が承認された場合）
2. 区分 B: 各ワークツリーの clean 再確認 → `git worktree remove <path>`（`--force` 禁止）→ `git worktree prune`
3. 区分 A: `git branch -d <branch>...`（`-D` 禁止。拒否されたら区分誤りなので消さずに報告）
4. 区分 C: ユーザー向けに `git branch -D <branch>` のコマンドと根拠（PR 番号・MERGED 実測）を提示して手動実行を依頼

途中でコマンドが拒否された場合（git の安全弁・プロジェクトのフックいずれでも）、それは「分類か証拠が間違っていた」シグナルとして扱う。強制オプションで押し切らず、対象を D に戻して報告する。

## Step 5: 結果報告

消したもの・残したもの・ユーザーに委ねたものを表で報告する（列: 区分/対象/結果/根拠）。「残した理由」も1行ずつ書く — 次回の掃除で同じ調査を繰り返さないため。

## 禁止事項

- `git branch -D`・`git worktree remove --force`・`git push --delete`・`git update-ref -d` を自分で実行すること（提示のみ可）
- 棚卸しと承認を飛ばしていきなり消し始めること
- リポジトリ外のワークツリー（進行中の作業ディレクトリ）を、ユーザーの個別指名なしに候補へ載せること
- 「たぶんマージ済み」「名前からして不要そう」という推測を根拠に削除すること — 根拠は必ず `--merged` の実測か PR の MERGED 実測
